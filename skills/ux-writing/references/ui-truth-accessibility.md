# UI 사실성과 접근성 연결

화면 전체나 폼, 상태 메시지, 동적 알림을 작성하거나 검토할 때 읽는다. 단건 링크,
아이콘 버튼, 대체 텍스트, 입력 오류 연결을 요청받았을 때도 읽는다. 이 문서는 문구와
제품 동작을 맞추고, 그 문구가 보조기술에도 전달되는지 구현 확인 항목을 분리하는
기준이다.

## 먼저 확보할 사실

다음 자료에서 확인되는 범위만 문구에 쓴다.

- 상태 정의: 데이터 없음, 로딩 또는 처리 중, 실패, 권한 제한, 완료
- 사용자 액션: 각 버튼과 링크가 실제로 실행하는 동작과 이동하는 위치
- 시스템 응답: 클라이언트 검증, 서버 접수, 비동기 처리 완료 중 어디까지 확인됐는지
- 입력 규칙: 필수 여부, 허용 형식과 범위, 오류를 고치는 방법
- 복구 수단: 재시도, 취소, 되돌리기, 문의가 실제로 제공되는지

근거가 없으면 원인, 시간, 금액, 기능, 복구 수단을 추정하지 않는다. 필요한 문구를
확정하려면 무엇을 알아야 하는지 `확인 필요`로 보고한다.

## 화면을 한 묶음으로 읽기

입력명, 도움말, 오류, 주요 액션, 제출 뒤 알림을 순서대로 읽는다. 사용자가 다음
행동을 이해하려면 화면에 존재하는 요소에 해당하는 질문을 확인한다.

1. 지금 무엇을 입력하거나 확인하는가?
2. 조건을 어겼다면 어느 입력이 왜 문제인가?
3. 어떻게 고칠 수 있는가?
4. 버튼을 누르면 무엇이 일어나는가?
5. 누른 뒤 접수, 처리 중, 완료 중 어디까지 진행됐는가?

정상적인 빈 상태는 오류처럼 사과하거나 재시도를 권하지 않는다. 실패는 데이터가
없다고 쓰지 않는다. 처리 중에는 완료를 선언하지 않고, 권한 제한에는 실제 요청
경로나 담당자가 확인될 때만 해결 방법을 안내한다.

비슷해 보이는 상태도 발생 원인과 다음 행동으로 나눈다.

- 비어 있는 목록은 최초 사용이라 아직 만든 항목이 없는지, 검색 조건에 맞는 결과가
  0개인지, 사용자가 항목을 모두 정리했는지 구분한다. 생성, 검색 조건 변경처럼 실제로
  가능한 행동만 제안한다.
- 온보딩의 필수 단계와 건너뛸 수 있는 단계를 제품 흐름대로 표시한다. 실제로 건너뛸
  수 없는 단계에 `나중에`를 만들거나, 선택 단계에 필수처럼 압박하는 문구를 쓰지 않는다.
- 처음 개인정보나 장치 권한을 요청할 때는 왜 필요한지, 언제 사용하는지, 거절하면
  실제로 어떤 기능이 제한되는지 알려준다. 이미 거절했거나 아직 권한이 없는 상태에서
  다시 허용하는 방법은 운영체제와 제품에 실제 경로가 확인될 때만 안내한다.
- 조치가 필요한 알림은 확인된 조치와 기한을 드러낸다. 단순 정보 알림은 즉시 대응이
  필요한 것처럼 방해하지 않는다. 기한과 긴급성을 추정해 높이지 않는다.

## 보조기술 전달 확인

문구 검토와 접근성 구현 검토를 연결하되 둘을 같은 일로 보지 않는다.

- 폼 컨트롤에는 목적을 설명하는 라벨이 필요하다. HTML에서 명시적으로 연결했다면
  `label`의 `for`와 컨트롤의 `id`가 같은 값인지 확인한다. `label`이 컨트롤을 감싸는
  암시적 연결처럼 의미상 연결이 성립하는 방식도 인정한다. placeholder만으로 라벨을
  대신하지 않는다.
- 보이는 버튼이나 입력명이 있으면 접근 가능한 이름에 그 보이는 문구가 같은 순서로
  포함되는지 확인한다. 문구를 바꿨다면 접근 가능한 이름도 함께 점검한다.
- 아이콘만 있는 버튼에는 실제 동작을 나타내는 접근 가능한 이름을 제공한다. 같은
  `자세히 보기` 링크가 반복되면 각 링크의 대상을 보조기술 사용자가 구별할 수 있는지
  확인한다. 보이는 문구가 없는 컨트롤도 이름과 동작 정보가 필요하다.
- 도움말과 오류에는 식별자를 두고 해당 입력의 `aria-describedby`에서 참조하는 등,
  설명과 입력 사이의 기술적 관계를 확인한다. 오류 상태는 문구만 보이는 데 그치지
  않고 `aria-invalid` 등으로 입력에 전달됐는지 본다.
- 여러 오류를 요약하면 각 항목에서 해당 입력으로 이동할 수 있는 링크를 제공하는지
  확인한다. 제출 뒤에는 첫 오류로 초점을 옮기는 방법도 검토한다.
- 동적으로 나타나는 오류와 상태 알림은 보조기술이 변화를 알 수 있도록 구현됐는지
  확인한다. 입력하는 동안의 일반 안내에는 `aria-live="polite"`처럼 현재 낭독을
  방해하지 않는 전달을 고려한다. 모든 변화를 `assertive`나 `alert`로 보내지 않고,
  즉시 알려야 할 오류인지에 따라 우선순위를 정한다.
- 색, 테두리, 아이콘만으로 성공과 실패를 구분하지 않는다. 상태를 말로도 전달한다.
- 정보가 없는 장식 이미지는 빈 대체 텍스트로 보조기술의 반복 낭독을 피할 수 있다.
  이미지가 정보를 전달하는지는 그 화면에서 이미지를 넣은 목적을 확인해 판단한다.
  완료 문구 옆 그림이 같은 내용을 반복하면 그림만 낭독에서 제외하며, 버튼이나 링크
  같은 컨트롤 자체를 보조기술에서 숨기지 않는다.

코드, 디자인 명세, 접근성 트리 또는 실제 보조기술 동작을 보지 못했다면 문구만
검사한 결과다. 구현 항목은 `확인 필요`로 남기며 WCAG 준수를 완료했다고 선언하지
않는다.
