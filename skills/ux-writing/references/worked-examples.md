# 화면 단위 윤문 예시

한 줄짜리 예시로는 안 보이는 것들 — 빈 문장 제거, 충돌 우선순위, 다음 행동
힌트 — 은 여러 요소가 같이 있는 화면에서 드러난다. SKILL.md의 원칙을 실제
화면에 어떻게 겹쳐 적용하는지 보여주는 예시 모음이다.

## 업로드 실패 다이얼로그

업로드 실패는 확인됐지만 원인은 알 수 없고, 다이얼로그 버튼은 창만 닫는 상황이다.
재시도 기능이 화면 다른 곳에 있더라도 아래 버튼의 동작은 달라지지 않는다.

```
[BEFORE]
제목:  오류가 발생하였습니다
본문:  파일 업로드를 진행하는 과정에서 알 수 없는 오류가 발생하여
       작업이 정상적으로 완료되지 못하였습니다. 다시 시도해 주시기 바랍니다.
버튼:  확인

[AFTER]
제목:  파일을 못 올렸어요
버튼:  닫기
```

무엇을 바꿨나

- **제목**: `명확` 먼저(무슨 일인지), 그 위에 `숨은 감정 공감`(딱딱한 "오류
  발생" 대신 사용자 입장). 충돌 우선순위대로 명확이 먼저, 감정은 그 위에.
- **본문**: 제목과 버튼에 없는 정보가 없어 생략. 시스템이 원인을 알려주지 않았으므로
  인터넷 연결이나 일시 장애를 원인으로 만들지 않음.
- **버튼**: 창을 닫는 실제 동작에 맞춰 "확인"을 "닫기"로 바꿈.

원인을 모르는 것이 확인된 상태라면 실패 사실만으로 문구를 낼 수 있다. 재시도
가능 여부를 모르면 재시도를 안내하지 않고, 필요하면 해당 조치만 `확인 필요`로
남긴다.

## 정상적인 빈 상태와 조회 실패

```
[상태 A: 사용자가 아직 만든 항목이 없음]
제목: 아직 만든 보고서가 없어요
본문: 첫 보고서를 만들면 이곳에서 확인할 수 있어요.
버튼: 보고서 만들기

[상태 B: 목록 요청이 실패함]
제목: 보고서를 불러오지 못했어요
본문: 다시 불러와 주세요.
버튼: 다시 불러오기
```

목록이 비었다는 화면만 보고 서버 오류 문구를 쓰거나, 요청 실패를 빈 상태로
표현하면 현재 상태와 다음 행동이 모두 틀어진다. 상태 A의 생성 버튼과 상태 B의
재요청 버튼이 실제로 제공된다는 전제이며, 구현이 다르면 문구도 그 동작에 맞춘다.

## 신청 폼과 접수 알림

```
입력명: 연락받을 이메일
도움말: 답변을 받을 주소를 입력해 주세요.
오류: 연락받을 이메일을 입력해 주세요.
버튼: 검토 요청 보내기
접수 알림: 검토 요청을 받았어요.
```

서버가 요청을 저장했다는 사실만 확인된 상황이다. `검토가 완료됐어요`나 답변 시간을
덧붙이지 않는다. 화면에서는 입력명과 오류가 같은 대상을 같은 이름으로 부른다.
구현에서는 입력명과 컨트롤, 오류 설명이 연결되고 동적으로 나타난 접수 알림이
보조기술에도 전달되는지 별도로 확인한다. 코드나 실행 화면을 보지 못했다면 이
접근성 항목은 `확인 필요`다.

## 권한이 없는 다운로드

```
제목: 이 파일을 다운로드할 권한이 없어요
본문: 파일 소유자에게 접근 권한을 요청해 주세요.
버튼: 닫기
```

권한 부족과 파일 없음은 다른 상태다. 본문의 요청 경로는 파일 소유자가 실제로
표시되거나 연락할 수 있을 때만 쓴다. 제품 안에 `권한 요청` 기능이 없는데 그런
버튼을 만들거나, 승인 시간을 약속하지 않는다.

## 검색 결과 0건과 검색 실패

전제: 검색어 수정 기능과 `다시 검색` 버튼이 실제로 있다.

```
[검색 완료, 결과 0건]
제목: "분기 보고서" 검색 결과가 없어요
본문: 검색어를 바꿔 보세요.

[검색 요청 실패]
제목: 검색하지 못했어요
버튼: 다시 검색
```

결과 0건은 정상 응답이고 검색 실패는 오류다. 실패를 `검색 결과가 없어요`로
표시하지 않는다. 검색어 수정이나 재검색 동작이 없다면 안내와 버튼도 넣지 않는다.

## 선택 온보딩과 첫 권한 요청

전제: 알림 설정은 선택 사항이고 `나중에` 동작이 있으며, 사용자가 배송 알림을 켤
때 운영체제 알림 권한을 요청한다.

```
[온보딩]
제목: 배송 상태를 알림으로 받을 수 있어요
버튼: 알림 설정
보조 버튼: 나중에

[알림 설정을 선택한 뒤 권한 요청 전]
본문: 상품 출발 알림을 보내려면 알림 권한이 필요해요.
버튼: 계속
```

선택 단계를 완료 조건처럼 쓰지 않는다. 권한은 필요한 기능을 선택한 시점에 목적을
설명한다. `나중에`나 대안이 실제로 없다면 문구로 만들지 않는다.

## 아이콘 버튼의 이름

전제: 돋보기 아이콘 버튼은 현재 보고서 목록의 검색창을 여는 동작을 한다.

```jsx
<button aria-label="보고서 검색 열기"><SearchIcon aria-hidden="true" /></button>
```

보이는 텍스트가 없는 버튼에는 동작 대상을 포함한 접근 가능한 이름을 둔다. 장식
아이콘은 보조기술에서 숨기되 버튼 자체를 숨기지 않는다. 버튼이 검색을 바로
실행한다면 이름도 실제 동작에 맞게 바꾼다.

## 파괴적 확인의 범위

전제: `프로젝트 삭제`는 현재 프로젝트와 그 안의 파일을 영구 삭제하지만 팀 계정과
다른 프로젝트에는 영향을 주지 않는다. 취소와 삭제 버튼이 실제로 있다.

```
제목: 프로젝트를 삭제할까요?
본문: 이 프로젝트와 안에 있는 파일이 영구 삭제돼요. 팀 계정과 다른 프로젝트는
      그대로 유지돼요.
버튼: 프로젝트 삭제
보조 버튼: 취소
```

`모든 데이터가 삭제됩니다`처럼 범위를 넓히지 않는다. 되돌릴 수 없음과 영향을
받는 대상을 확인된 범위대로 쓰고, 파괴적 버튼에는 대상을 포함한다.

## 기본 모드와 딥모드

전제: 원문은 작성자가 직접 쓴 후기이며, 기다린 시간과 감정은 모두 원문에 있다.
목표 register는 해요체다.

```
[원문]
결과가 나오기까지 사흘을 기다렸습니다. 기다리는 동안 접수가 됐는지 몰라서 가장
답답했습니다.

[기본 모드]
결과가 나오기까지 사흘을 기다렸어요. 기다리는 동안 접수 여부를 알 수 없었던 점이
가장 답답했어요.

[딥모드]
결과가 나오기까지 사흘을 기다렸어요. 그동안 접수가 됐는지 알 수 없었던 게 가장
답답했어요.
```

두 모드 모두 기다린 기간과 `가장`이라는 강조를 보존한다. 기본 모드는 뜻과 어체를
정리하고, 딥모드는 작성자가 직접 쓴 개인 후기의 말맛을 더 살린다. 대기 원인이나
서비스 평가를 새로 보태지 않는다.
