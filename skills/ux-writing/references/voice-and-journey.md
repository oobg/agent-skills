# 보이스와 여정 카피

보이스 가이드를 만들거나, 같은 제품의 상황별 톤과 여러 화면에 걸친 과업을 점검할 때
읽는다. 단건 윤문에는 차트나 여정 지도를 새로 만들 필요가 없다. 기존 브랜드 규칙,
glossary와 register를 먼저 따른다.

## 보이스를 문구에 적용하기

보이스는 제품이 유지할 성격이다. 톤은 현재 상황에 맞춰 조절하는 표현이다. 어미만
통일해서는 둘을 판단할 수 없다. 브랜드 자료와 타깃 사용자의 기대를 바탕으로 원칙을
좁힌다. 원칙마다 실제로 쓸 표현과 피할 표현을 연결한다. 브랜드 근거가 없으면 가정을
적은 초안으로 제시한다. 이를 프로젝트의 확정 규칙으로 저장하지 않는다.

차트에는 제품 원칙, 사용자 과업과 상황, 표현 규칙, 문구 예시를 연결한다. 감정은
사용자 발화나 관찰이 없으면 가능성으로 다룬다. 상황에 따라 용어, 문장 구조, 구두점과
설명량 중 필요한 것만 정한다. 모든 제품에 같은 원칙 수나 글자 수를 강제하지 않는다.

아래는 합성한 작업 관리 제품의 예다. 프로젝트는 합니다체이며 보이스는 '차분하게
진행을 돕는다'로 정해져 있다. 저장과 입력 조건은 제품 명세로 확인됐다고 가정한다.

| 제품 원칙 | 과업과 상황 | 표현 규칙 | 적용 문구 | 피할 표현 |
| --- | --- | --- | --- | --- |
| 다음 행동을 구체적으로 안내 | 첫 작업 작성, 익숙하지 않을 수 있음 | 제목으로 대상을 알리고 설명은 첫 행동만 안내 | 첫 작업을 만들어 보세요. / 버튼: 작업 만들기 | 일단 시작해 볼까요?! |
| 진행을 정확히 전달 | 저장 완료, 작업을 이어가려는 순간 | 결과 한 문장, 과한 축하 생략 | 작업을 저장했습니다. | 완벽하게 해냈습니다! |
| 수정할 곳을 바로 안내 | 제목 누락, 막막할 수 있음 | 입력명과 필요한 수정, 감탄부호 생략 | 작업 제목을 입력해 주세요. | 아차! 제목을 깜빡하셨네요! |

같은 어체 안에서도 첫 안내는 행동을 돕고, 완료는 짧게 알리며, 오류는 수정에 집중한다.
보이스를 살리려고 실패를 축하하거나, 해결 가능성이 확인되지 않은 안심을 덧붙이지 않는다.
기존 가이드와 어긋나는 새 톤은 제안으로 구분한다.

## 과업의 앞뒤를 잇기

화면별 사실과 접근성은 [UI 사실성과 접근성 연결](ui-truth-accessibility.md)을 따른다.
여러 화면을 볼 때는 사용자의 목표 하나를 정하고 앞 화면의 약속이 뒤 화면에서도
지켜지는지 확인한다. 동기는 사용자가 얻는 가치와 필요한 행동을 설명하는 데 쓰며
혜택 문구가 실제 버튼 동작을 가리지 않게 한다.

| 단계 | 문구로 답할 질문 | 앞뒤 대조 |
| --- | --- | --- |
| 행동 전 | 왜 필요한가, 다음에 무엇을 하게 되는가? | 제목과 버튼이 다음 화면이나 실행 결과를 예고하는가? |
| 행동 중 | 무엇을 어떤 조건으로 입력하거나 선택하는가? | 앞에서 부른 대상과 용어가 같으며 필요한 조건이 제때 보이는가? |
| 행동 후 | 어디까지 진행됐고 다음에 무엇을 할 수 있는가? | 앞의 약속과 실제 상태가 맞으며 가능한 다음 행동으로 이어지는가? |

모든 단계에 문장을 추가하지 않는다. 기존 라벨이나 UI만으로 충분하면 유지한다.
알 수 없는 결과나 복구 경로는 문구로 채우지 말고 확인 항목으로 분리한다.

합성 예시: 보고서 설정 화면으로 이동하는 버튼이 있고 그 다음 화면에서 기간을
고르면 비동기 생성 요청을 보낸다. 서버가 요청을 접수했다는 사실만 확인됐다.

```text
전: 버튼 '보고서 받기' → 기간 선택 → 버튼 '완료' → '보고서가 완성됐습니다.'
후: 버튼 '보고서 만들기' → 기간 선택 → 버튼 '생성 요청' → '보고서 생성을 요청했습니다.'
확인 필요: 생성 완료를 확인할 위치와 알림 수단. 완료 시간이나 다운로드 경로는 만들지 않는다.
```

## 선택을 오해하게 하는 문구 찾기

선택 항목은 선택했을 때와 선택하지 않았을 때를 각각 평문으로 설명해 본다. 체크박스의
실제 값과 표시 상태까지 대조해야 한다. 이중 부정을 지우면서 논리를 뒤집거나, 부정적인
결과를 부드럽게 포장해 숨기지 않는다. 모호한 문구만으로 제작자의 의도를 단정하지 않는다.

```text
확인된 동작: 선택하면 추천 소식을 받고, 미선택이면 받지 않는다. 선택 사항이다.
원안: '추천 소식을 받지 않으려면 선택하지 마세요.'
수정안: '추천 소식 받기 (선택)'
검토: 선택/미선택의 결과가 그대로다. 저장 방식과 기본 선택 상태는 별도 구현 확인 대상이다.
```

정책이나 고정 고지를 바꿔야 하는 경우는 문구 수정과 분리하고 기존 멈춤 규칙을 따른다.

## 적용 결과 확인

자료가 있으면 타깃 사용자의 실제 언어와 대조한다. 자료가 없는 합성 사례 검토는 실제
사용성 검증으로 부르지 않는다. 사용성 평가를 수행하는 작업이라면 목표와 현실적인
맥락을 주고 버튼명을 정답처럼 알려주지 않은 상태에서 다음 행동과 결과를 어떻게
이해하는지 본다. 선호하는 문구를 고르게 하는 것만으로 과업 이해를 확인했다고 하지 않는다.
