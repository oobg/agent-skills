# UX Writing

제품 UI와 사용자에게 공개되는 문장을 명확하고 자연스럽게 다듬는 에이전트
스킬입니다. AI 티를 지우는 것보다 원문의 의미와 프로젝트 보이스를 보존하는 일을
먼저 봅니다.

## 사용 시점

- 버튼, 라벨, 에러 메시지, 빈 상태 문구를 다듬을 때
- 실제 상태와 버튼 동작에 맞춰 화면 전체 문구를 점검할 때
- 링크, 아이콘 버튼, 대체 텍스트, 입력 오류와 동적 알림의 접근성 전달을 점검할 때
- README, 가이드, 릴리스 노트의 어체를 정리할 때
- 번역투나 기계적인 AI 문체를 줄이고 싶을 때
- 프로젝트 용어와 브랜드 보이스를 일관되게 적용할 때
- 상황별 톤 가이드를 만들거나 여러 화면의 약속과 결과를 연결해 점검할 때
- 결제, 삭제, 보안처럼 위험이 큰 문구를 별도로 검증할 때

## 적용 강도

| 강도 | 대상 | 적용 범위 |
| --- | --- | --- |
| 경량 | 내부 문서, 코드 주석 | 정확성과 명확성 |
| 표준 | 제품 UI, 외부 README와 가이드 | 체크리스트와 출력 게이트 |
| 고위험 | 결제, 삭제, 보안, 법률, 접근성 | 정확성 우선, fresh-eyes 감사 추가 |

프로젝트의 glossary, register, 브랜드 규칙이 기본 `~해요`체보다 우선합니다.

## 핵심 원칙

충돌할 때는 다음 순서를 따릅니다.

```text
정확 → 명확 → 간결 → 감정
```

- 확실성, 인과, 행위자, 수치, 긍정과 부정을 바꾸지 않습니다.
- 정상적인 빈 상태, 실패, 처리 중, 권한 제한과 접수, 완료를 구분합니다.
- 확인되지 않은 원인, 시간, 금액, 기능과 복구 수단을 만들지 않습니다.
- 입력명, 도움말, 오류, 액션과 알림을 함께 읽어 다음 행동이 이어지는지 봅니다.
- 쉬운 말은 타깃 사용자의 언어와 과업을 기준으로 판단합니다. 전문가에게 익숙한
  용어는 제품 UI에서도 유지합니다.
- 보이스 차트로 제품의 성격과 상황별 표현을 연결하고, 행동 전 안내부터 행동 후
  결과까지 약속이 이어지는지 확인합니다. 차트는 필요한 작업에서만 작성합니다.
- 선택과 미선택의 결과를 대조해 목적 은폐와 이중 부정으로 생기는 오해를 점검합니다.
- 멀쩡한 문장은 고치지 않습니다.
- 과윤문과 장르 이탈도 실패로 봅니다.
- 관점이나 실제 경험을 지어내지 않습니다.
- AI 문체는 단일 표현으로 판정하지 않고 수사, 어휘 밀도, 구조 규칙성을 함께 봅니다.
- 정당한 대비와 불확실성, 필요한 목록, 짧은 UI 구조는 보존합니다.
- 이모지, 곱슬따옴표, 대시 같은 스타일 신호는 문맥으로 판단합니다.
- lint의 HARD 0은 좋은 글을 보증하지 않습니다.

## 사용 예

```text
이 결제 실패 메시지를 더 명확하게 다듬어줘. 의미와 오류 코드는 유지해줘.
```

```text
이 README의 프로젝트 어체는 유지하면서 번역투와 AI 티만 줄여줘.
```

정서까지 보강하려면 `/ux-writing:deep` 또는 “정서까지 살려줘”라고 요청합니다.
`/ux-writing:deep`은 앱에 등록된 명령이 아니라 메시지에 쓰는 모드 지정입니다.
같은 메시지에 원문을 붙이거나 현재 작업 대상을 분명히 지정해야 하며, 대상이 없으면
스킬이 원문을 요청합니다.

```text
/ux-writing:deep

결과가 나오기까지 사흘을 기다렸습니다. 기다리는 동안 접수가 됐는지 몰라서 가장
답답했습니다.
```

기본 모드는 의미를 보존하며 명확성, 간결성, AI 문체를 고칩니다. 딥모드는 기본
교정 뒤 원문에 이미 있는 정서와 관점을 살립니다. 사실, 수치, 확실성, 장르와
프로젝트 어체는 두 모드 모두 바꾸지 않습니다.

화면 단위 작업에서는 문구가 보조기술에 전달되도록 라벨, 오류 설명, 상태 알림의
구현 연결도 확인합니다. 코드나 실행 결과를 확인하지 못한 부분은 확인 필요로
남기며, 문구 검사만으로 접근성 준수를 완료했다고 판단하지 않습니다.

## 검사 도구

Python 3.8 이상에서 실행합니다.

```bash
python3 <ux-writing 스킬 폴더>/scripts/ai_lint.py <파일>
python3 <ux-writing 스킬 폴더>/scripts/glossary_check.py <파일>
python3 <ux-writing 스킬 폴더>/scripts/register_check.py <파일>
```

- `ai_lint.py`: 결정적인 문법 오류와 스타일 신호 검사
- `glossary_check.py`: 프로젝트 고정 표기 검사
- `register_check.py`: 해요체, 합니다체, 한다체, 음슴체, 명사형의 목표 어체
  일관성 검사. 음슴체와 명사형은 서로 안전하게 자동 구분하기 어려워 명확한 다른
  어체의 혼용만 잡으므로 사람이 직접 확인해야 하고, 그 확인도 best-effort입니다.

HARD 항목은 출력을 막지만 ADVISORY는 문맥을 확인하라는 신호입니다. 현재 HARD
검사는 결정적 기계 오류와 모든 가운뎃점을 잡는 smoke check이며 전체 문장 품질을
인증하지 않습니다.
딥모드의 정서 적합성과 사실 보존, 실제 UI 동작과 접근성 연결은 원문과 제품 맥락을
대조해 검토합니다.
`<ux-writing 스킬 폴더>`는 현재 로드한 `SKILL.md`의 상위 폴더로 바꿉니다.

## 구성

```text
ux-writing/
├── SKILL.md
├── agents/
│   └── copy-auditor.md
├── references/
│   ├── about.md
│   ├── ai-tells.md
│   ├── deep-mode.md
│   ├── glossary.md
│   ├── ontology-boost.md
│   ├── register.md
│   ├── setup.md
│   ├── translation-ese.md
│   ├── ui-truth-accessibility.md
│   ├── voice-and-journey.md
│   └── worked-examples.md
└── scripts/
    ├── ai_lint.py
    ├── glossary_check.py
    ├── patterns.json
    └── register_check.py
```

- [`SKILL.md`](SKILL.md): 적용 범위, 원칙, 출력 게이트
- [`references/`](references): 화면 단위 사실성과 접근성, 어체, 긴 글처럼 해당 작업에
  필요할 때만 여는 상세 규칙과 예시
- [`agents/copy-auditor.md`](agents/copy-auditor.md): 배치와 고위험 문구의 fresh-eyes 점검
- [`scripts/`](scripts): 기계적으로 판정할 수 있는 검사

설치와 검증 방법은 저장소의 [루트 README](../../README.md)에서 확인할 수 있습니다.
