# guide — 따라하기·사용 가이드

**패턴: 어떻게 하나? 내 상황엔 어떻게 쓰나?** 페이지 타입이 아니라 이 질문에 답하는 섹션의 표현 방식이다. 다른 패턴 섹션과 한 페이지에 섞어 쓴다(섹션 `data-pattern="guide"`, 사용 가이드는 같은 섹션의 `data-variant="practice"`).

guide는 독자가 읽고 나서 올바르게 실행하거나 사용하게 만드는 패턴이다. 변형은 두 가지다.

| 변형 | 표기 | 독자 질문 | 대표 도식 |
|---|---|---|---|
| 따라하기(기본, 실행) | 없음 | 이걸 어떻게 하지? | 단계별 화면 와이어프레임 |
| 사용 가이드(잘 쓰기) | `<section data-pattern="guide" data-variant="practice">` | 이걸 어떻게 잘 쓰지? 내 상황엔 뭘 고르지? | 상황·역할별 갈림 경로 graph 또는 원칙 카드 |

`data-variant="practice"`는 변형을 표시하는 이름표다. 스타일은 바꾸지 않는다.

## 요청 신호

- 따라하기: "따라하기", "설치 가이드", "설정 방법", "온보딩 안내", "체크리스트로".
- 사용 가이드: "잘 쓰는 법", "사용 가이드", "베스트 프랙티스", "언제 뭘 써야 해", "역할별 사용법", "운영 원칙".

## 섹션으로 쓸 때

- 다른 패턴이 이끄는 페이지에서 "직접 해 보려면"이 질문 하나로 나오면 따라하기 섹션 하나(checklist, 단계 많으면 구간으로)로 답한다.
- 추천 블록: [checklist](../blocks/checklist.md) 기본·연동 변형, [code-block](../blocks/code-block.md), 막혔을 때 [faq](../blocks/faq.md). 사용 가이드는 원칙 카드·갈림 경로 graph. 구도는 Spotlight 또는 Sequence.

## 함께 자주 섞는 패턴

- preview·flow로 "무엇이고 어떻게 흐르나"를 보인 뒤 "직접 해 보기"로, faq를 막혔을 때 섹션으로.

## explanation 쓰는 곳

- 사용 가이드의 원칙·경로 옆에 `reason`(왜 그렇게 쓰나)과 `exception`(이 상황이면 다른 길). 따라하기 단계 안 설명은 행의 예상 결과 한 줄이 맡고, 구간 결과는 구간 머리 행의 결과 한 줄, 다 끝난 뒤 할 일은 closing이다.

## 추천 조합

완료 화면 + checklist linked(구간: 전체 진행률 한 줄 + 구간 머리 행이 지도, 현재 구간만 펼침) + code-block + question-answer(막혔을 때) + closing `criteria`. 블록은 패턴이 소유하지 않는다. 다른 패턴 문서의 블록도 필요하면 그대로 빌린다([blocks.md](../blocks.md)).

## 따라하기 (기본)

### 이 패턴이 답하는 질문

- 전부 하는 데 얼마나 걸리는가?
- 시작 전에 무엇을 준비해야 하는가(권한·준비물)?
- 지금 몇 단계까지 했고, 각 단계가 끝났는지 어떻게 아는가?
- 막히면 어떻게 하는가?
- 다 끝나면 다음에 무엇을 하는가?

### 대표 도식

단계별 화면 와이어프레임(diagram wireframe). 단계마다 "누를 곳" 하나만 블루.

### 뼈대

시작 전 조건 → 구간 → 단계(한 단계 한 행동 + 예상 결과 + 막힘 해결) → 단계별 화면·설명 → 확인 → 다음 단계.

**구간.** 한 화면에서 사용자가 선택하거나 기억해야 하는 상세 단계가 많으면, 현재 작업 단위만 펼쳐 보여준다. 단계가 길어지면 작업 목적이 바뀌는 지점에서 구간으로 나누고(한 구간 보통 3~5단계, 숫자로 기계적으로 자르지 않는다), 구간 이름은 끝나면 얻는 결과로 짓는다. 판단 기준·마크업·동작은 [checklist](../blocks/checklist.md) 구간 절이 정본이다.

### 페이지 주 패턴일 때 (자연스러운 깊이 4~7)

이 패턴이 페이지 대부분을 차지할 때의 출발점이다. 깊이는 참고값이고 섹션 수는 독자 질문이 정한다. 첫 화면 섹션은 그림이 필수이고, 그 아래 섹션은 핵심 구조가 있으면 그림을 권장한다. 아래를 전부 채우지 않는다.

header(리드에 총 소요 시간. 소요 시간을 모르면 단정하지 않고 생략한다) → ① 끝나면 이렇게 보여요: 완료 화면 와이어프레임 → ② 따라 하기: checklist `data-variant="linked"`(왼쪽 sticky 단계 화면이 행 호버·포커스·클릭·체크에 따라 그 단계 그림으로 바뀜, 오른쪽 행마다 단계 제목·예상 결과 한 줄) → ③ 막혔을 때: [faq](../blocks/faq.md) 답글형(질문→답 구조라 그림 없음).

② linked 무대도 그림 블록이다. 붙여 넣을 명령·설정·입력 예시는 그 행의 `<details>` 안에 [code-block.md](../blocks/code-block.md)(복사 버튼)로 둔다.
단계가 둘 이하이거나 단계마다 화면이 바뀌지 않으면 linked 대신 기본 checklist를 쓰고 그림은 ①에만 둔다.

시작 전 조건(권한·준비물)은 ② 위 한 줄 행으로 둔다(섹션을 따로 만들지 않는다). 첫 단계를 하기 전에 독자가 알아야 한다.
단계 제목은 사용자가 하는 동작 하나로, 예상 결과 한 줄은 "끝나면 보이는 것"으로 쓴다("저장하면 상태가 '켜짐'으로 바뀌어요").
특정 단계에서 자주 막히면 그 행의 `<details>` 안에 해결 한 줄을 두고, 여러 단계에 걸친 문제는 ③으로 모은다.
마지막 행은 완료 확인(① 화면과 같은지)으로 끝내고, 문서 끝 다음 단계는 closing `criteria` 또는 `action`([closing](../blocks/closing.md))으로 맺는다.

소요 시간을 생략하면 첫 독자 질문은 준비물과 "끝나면 보이는 것"(① 완료 화면)으로 답한다. 행마다 시간을 지어내지 않는다.
담당·기한이 없는 할 일은 `data-meta="none"`으로 메타 열을 비운다.

합성 예: "주문 내보내기 자동 전송 켜기: 약 10분".

### 안티패턴

- 핵심 구조가 있는 섹션을 그림 없이 문단으로만 채우기, 질문 없이 추천 블록을 전부 채우기, 짧게 만들려고 이유·조건을 지우기.
- 총 단계 수로 자르기("5단계 넘으면 접기"), 또는 단계가 길고 무거운데 구간 없이 한 목록으로 늘어놓기. 상한은 한 번에 이해해야 하는 작업량에 건다([checklist](../blocks/checklist.md) 구간).
- 추상어 구간 이름(`준비`·`설정`)만 있고 구간 머리에 얻는 결과 한 줄이 없음. 구간 이름·결과·진행 수를 rail·별도 머리·checkpoint로 되풀이함.
- 시작 전 조건을 중간 단계에서야 알림(4단계에서 권한이 없음을 알게 함).
- 한 행에 행동 여러 개, 예상 결과가 없는 행.
- 완료 판정이 모호함("확인하기", "점검").
- 사용자가 할 일과 시스템이 하는 일이 한 목록에 섞임(시스템 일은 결과 한 줄로만).
- 명령을 본문 `p`나 결과 한 줄에 그대로 적기(복사할 코드는 code-block으로), 단계 그림을 행마다 복제하기(linked 무대 한 장으로).

## 사용 가이드 (`data-variant="practice"`)

### 이 패턴이 답하는 질문

- 이것은 무엇을 하려고 쓰는가(목적)?
- 쓰기 전에 무엇을 알아 둬야 하는가?
- 왜 그렇게 써야 하는가(기본 원칙)?
- 내 상황·역할에서는 어떤 경로를 고르는가?
- 무엇을 피해야 하는가?
- 다음에 무엇을 읽는가?

### 대표 도식

상황·역할별 갈림 경로 연결 그래프(diagram graph): 왼쪽에 상황·역할, 오른쪽에 추천 경로, 독자가 가장 많이 해당하는 갈림 하나만 블루.
원칙이 중심이면 원칙 카드(thumb-cards): 카드마다 원칙 하나를 작은 그림 + 한 줄 이유로.

### 뼈대

목적 → 먼저 알아둘 것 → 기본 원칙(왜) → 상황·역할별 추천 경로 → 사례 → 피해야 할 것 → 다음으로 읽을 것.

### 페이지 주 패턴일 때 (자연스러운 깊이 4~7)

이 패턴이 페이지 대부분을 차지할 때의 출발점이다. 깊이는 참고값이고 섹션 수는 독자 질문이 정한다. 첫 화면 섹션은 그림이 필수이고, 그 아래 섹션은 핵심 구조가 있으면 그림을 권장한다. 아래를 전부 채우지 않는다.

header(리드에 목적 한 문장, 먼저 알아둘 것은 리드 아래 한 줄) → ① 기본 원칙: 원칙 카드 3~5장(원칙마다 이유 한 줄) → ② 내 상황엔 이 길: 상황·역할별 갈림 경로 graph + step-columns 주석(경로마다 사례 한 줄) → ③ 피해야 할 것: side-by-side 전/후 카드 또는 accordion(구조 블록이면 그림 없음) → 다음으로 읽을 것은 closing `action`으로 맺는다.

사례는 따로 섹션을 만들지 않고 원칙 카드나 경로 주석 안에 짧게 둔다. 원칙과 경로 중 하나만 핵심이면 섹션 2개로 끝낸다.
추천은 제품이 아니라 독자 상황으로 쓴다("검토가 잦으면 A 경로, 혼자 쓰면 B 경로").

합성 예: "검토 요청 기능 잘 쓰기: 역할별 추천 경로".

### 안티패턴

- 원칙만 나열하고 이유(왜)가 없음.
- 모든 독자에게 같은 경로를 권함(상황·역할 갈림이 없음).
- 체크박스 실행 목록을 섞음(실행 절차는 따라하기 변형으로 나눈다).
- 기능 소개·장점 홍보로 채움(사용 가이드는 선택 기준과 쓰는 법이다).
- 피해야 할 것을 이유 없이 금지어 목록으로만 둠.
- 핵심 구조가 있는 섹션을 그림 없이 문단으로만 채우기, 질문 없이 추천 블록을 전부 채우기.

## 경계

- 체크박스로 직접 실행하면 guide 따라하기, 흐름 이해가 목적이면 flow, 잘 쓰는 법·선택 기준이면 guide 사용 가이드.
- 대상 두세 개를 같은 축으로 견주어 하나를 고르게 하면 compare, 내 상황에서 쓰는 법을 고르게 하면 guide 사용 가이드.

## 덱으로 낼 때

Deck Type **Demo**: `<main class="d0-deck" data-pattern="guide">`(사용 가이드면 `data-variant="practice"`). 규칙은 [deck](../output/deck.md).
덱은 함께 보며 시연할 때 쓴다. 독자가 혼자 체크하며 실행하면 page 따라하기가 낫다(덱에는 체크박스를 두지 않는다).

따라하기 스토리라인(표지 다음 제목 목차는 공통이라 생략):
상황 → 사용자 → Before → 제품 → 사용 흐름 → 실제 화면 → After

| 장 | `data-kind` |
| --- | --- |
| 상황 | `cover`(h1 = 끝나면 무엇을 할 수 있나) |
| 사용자 | 근거(누가, 무엇이 준비되어야 하나) |
| Before | `screenshot`(시작 화면) |
| 제품 | `assertion`(이 도구가 하는 일 한 문장) |
| 사용 흐름 | 근거(단계 도식, 5단계까지) |
| 실제 화면 | `screenshot`(누를 곳 spotlight + 번호 주석) |
| After | `closing`(`criteria`: 완료 화면과 같은지 + 다음 행동) |

Impact: 제품(`assertion`), 단계가 하나로 압축되는 핵심 화면이 있으면 그 `screenshot`.
사용 가이드 `practice`는 목적(`assertion`) → 기본 원칙(`breakdown`) → 내 상황엔 이 길(근거: 갈림 경로 graph) → 피해야 할 것(근거: 전/후) → 다음(`closing` `action`)로 바꾼다.
