# flow — 절차·구조 설명

**패턴: 어떻게 흘러가나? 어떤 부품이 어떻게 이어지나?** 페이지 타입이 아니라 이 질문에 답하는 섹션의 표현 방식이다. 다른 패턴 섹션과 한 페이지에 섞어 쓴다(섹션 `data-pattern="flow"`).

## 이 패턴이 답하는 질문

flow는 흐름을 이해하고 다음 행동을 아는 페이지다. 독자가 직접 체크하며 실행하는 페이지는 guide 따라하기가 맡는다.

- 무엇이 있어야 시작되는가(시작 조건)?
- 처음부터 끝까지 어떻게 흘러가고, 각 단계에서 누가 무엇을 하며 무엇이 나오는가?
- 잘 끝났는지 어떻게 아는가(성공 확인)?
- 막히면 어디서 멈추고 어떻게 되는가?
- 지금 어느 단계이고, 다음에 무엇을 하는가(해당할 때)?
- (구조 설명이면) 어떤 부품이 있고 서로 어떻게 연결되는가?

## 요청 신호

"어떻게 돌아가", "흐름 설명", "프로세스", "구조 그려줘", "아키텍처 쉽게", "개념 설명", "이제 뭐 하면 돼".

## 대표 도식

연결 그래프(diagram graph, 부품과 연결) 또는 단계 도식(같은 그림을 단계마다 조금씩 바꿔 그린 작은 SVG 3~5장).

## 흐름의 뼈대

시작 조건 → 단계(한 단계 한 행동, 단계마다 나오는 것) → 성공 확인 → 막히면 → 다음.

- 시작 조건을 맨 앞에 둔다. 중간 단계에서 권한·준비물이 없다는 걸 알게 하지 않는다.
- 한 단계에는 한 행동만 둔다. 단계마다 행동 뒤에 결과를 붙인다("검토를 요청하면 상태가 '대기'로 바뀌어요").
- 성공 확인은 눈에 보이는 결과 하나로 쓴다. "확인하기"처럼 모호하게 쓰지 않는다.
- 막히는 지점은 흐름 위에 표시하고 갈림(되돌아감·멈춤)을 그림에 그린다. 해결 절차를 길게 쓰지 않는다.
- 다음은 한 줄 행동으로 끝낸다. 실제 순서(준비→설정→실행→확인→운영)가 길면 한 페이지에 다 넣지 않고 다음 페이지로 넘긴다.

## 섹션으로 쓸 때

- 다른 패턴이 이끄는 페이지에서 "어떻게 쓰나", "어떻게 돌아가나"가 질문 하나로 나오면 흐름 섹션 하나로 답한다.
- 추천 블록: [flow-line](../blocks/flow-line.md) 한 줄 + 단계 도식 또는 연결 그래프([diagram](../blocks/diagram.md)), 단계 주석은 [step-columns](../blocks/step-columns.md). 구도는 Sequence 또는 Canvas.
- 성공 확인과 막히는 갈림은 섹션 안에 그대로 둔다.

## 함께 자주 섞는 패턴

- preview 다음 "어떻게 쓰나"로(기능 소개), incident 앞에서 "평소에는 어떻게 흐르나"로, faq의 용어 카드를 앞에 빌려 온다.

## explanation 쓰는 곳

- 단계 도식 옆 열에 `reason`(왜 이 순서인가)과 `exception`(어디서 갈라지나). 구조 그래프 아래에는 `interpretation`(한 부품을 고치면 어디까지 닿나).

## 추천 조합

flow-line + 단계 도식(status rail로 현재 단계) + step-columns + explanation `reason`·`exception` + checkpoint(성공 확인). 블록은 패턴이 소유하지 않는다. 다른 패턴 문서의 블록도 필요하면 그대로 빌린다([blocks.md](../blocks.md)).

## 페이지 주 패턴일 때 (자연스러운 깊이 4~6)

이 패턴이 페이지 대부분을 차지할 때의 출발점이다. 깊이는 참고값이고 섹션 수는 독자 질문이 정한다. 첫 화면 섹션은 그림이 필수이고, 그 아래 섹션은 핵심 구조가 있으면 그림을 권장한다. 아래를 전부 채우지 않는다.

header(문장형 리드, 시작 조건을 한 줄로) → ① 전체 모양: flow-line 한 줄 + 연결 그래프 또는 단계 도식(막히는 갈림 포함) → ② 단계마다 무엇이 나오나: 단계별 미니 그림 카드(thumb-cards) + step-columns 주석, 마지막 단계에 성공 확인 → ③ (구조 설명이면) 부품 사이 관계: 연결 그래프에서 한 부품을 고쳤을 때 닿는 곳만 블루. 절차 설명이면 ③ 대신 closing `action`([closing](../blocks/closing.md))으로 다음 행동 한 가지를 맺는다.

사실 단계가 5를 넘으면 의미 단위로 묶어 2~5단계로 줄이고, 단계마다 그림 + 설명을 둔 [step-columns](../blocks/step-columns.md)의 그림+설명 단계 열 변형을 쓴다. 묶인 안쪽 단계는 설명 한 줄에 풀어 쓴다.

개념·구조 설명 요청도 이 패턴에서 다룬다. 용어가 많으면 용어 그림 카드(thumb-cards)를 빌려 온다.

합성 예: "주문 내보내기가 파일로 만들어지기까지", "팀 A의 검토 요청 흐름".

## 패턴 안티패턴

- 핵심 구조가 있는 섹션을 그림 없이 문단으로만 채우기, 질문 없이 추천 블록을 전부 채우기, 짧게 만들려고 이유·조건을 지우기.
- 6단계 이상(원칙 상한 5, 넘으면 큰 단계로 묶고 하위 페이지로 나눈다).
- 시작 조건이 없거나 중간 단계에서야 나옴.
- 단계 이름만 있고 단계마다 "누가·무엇이 나오나"가 없음, 한 단계에 행동 여러 개.
- 성공 확인 없이 끝나거나, 다음 행동 없이 끝남.
- 행마다 체크박스를 단 실행 목록(그건 guide 따라하기).
- 정보 없는 장식 그림.
- 추상 3D·홀로그램·네온 비주얼.

## 경계

- 체크박스로 직접 실행하면 guide 따라하기, 흐름 이해가 목적이면 flow, 잘 쓰는 법·선택 기준이면 guide 사용 가이드.
- 날짜가 붙으면 timeline, 순서만 있으면 flow.

## 덱으로 낼 때

Deck Type **Explainer**: `<main class="d0-deck" data-pattern="flow">`. 규칙은 [deck](../output/deck.md).

스토리라인(표지 다음 제목 목차는 공통이라 생략):
한 문장 정의 → 큰 그림 → 구성 요소 → 흐름 → 예시 → 예외 → 요약

| 장 | `data-kind` |
| --- | --- |
| 한 문장 정의 | `cover` 다음 `assertion`(비유 한 문장) |
| 큰 그림 | 근거(연결 그래프 전체, 가로로 길면 전체 폭) |
| 구성 요소 | `breakdown`(부품 2~5개, 지금 말하는 부품만 blue) |
| 흐름 | 근거(단계 도식 또는 [step-columns](../blocks/step-columns.md) 그림 변형) |
| 예시 | `screenshot` 또는 `evidence`(실제 한 건을 따라감) |
| 예외 | 근거(막히는 갈림을 그린 그래프) |
| 요약 | `closing`(`action`: 기억할 것 + 다음 행동) |

Impact: 한 문장 정의(`assertion`), 큰 그림(그림 하나만 둔 면).
구조 변경 기술 발표(예전 `tech`)는 문제 → 기존 구조(`breakdown`) → 병목(`evidence`) → 변경 구조(`breakdown`) → 전/후(`evidence`) → 트레이드오프(근거) → 다음(`closing` `action`)로 바꾼다.
