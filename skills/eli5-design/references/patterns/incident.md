# incident — 사건·원인

**패턴: 무슨 일이 어떤 순서로 왜 일어났나?** 페이지 타입이 아니라 이 질문에 답하는 섹션의 표현 방식이다. 다른 패턴 섹션과 한 페이지에 섞어 쓴다(섹션 `data-pattern="incident"`).

이 패턴은 일반 구조 기반이다. 외부 사례 근거가 약하므로 구성은 출발점으로만 쓴다.

독자는 읽고 나서 무슨 일이 왜 생겼는지 이해하고 재발을 막을 수 있어야 한다. 사람이 아니라 시스템을 본다.

## 이 패턴이 답하는 질문

- 언제 발생해 언제 복구됐고, 지금 상태는 무엇인가(해결·조치 중·조사 중)?
- 누가(대상), 어디까지(범위), 얼마나 오래(지속) 영향을 받았는가?
- 무슨 일이 어떤 순서로 일어났는가?
- 무엇이 방아쇠였고(직접 원인), 왜 그 방아쇠가 사고가 됐는가(근본 원인)?
- 다시 일어나지 않게 무엇을 하고, 무엇을 배웠는가?

## 요청 신호

"장애 정리", "사고 보고", "원인 분석 쉽게", "포스트모템", "무슨 일이 있었는지".

## 대표 도식

세로 타임라인(timeline vertical) + 영향 그래프(diagram graph: 고장 난 곳 red 노드 + 라벨, 영향받은 곳 블루, 영향 없던 곳 회색).
발생 시각이 없으면 세로 타임라인 대신 steps 도식(원인 단계 red, 조치 단계 blue-dark, 게이트 green)으로 순서만 그린다.
원인은 두 칸으로 나눈 그림이다. 트리거 노드 하나 → 그것을 막지 못한 구조(빠진 검사·한계값·단일 경로)를 graph 한 장에 이어 그리고, 트리거는 red, 근본 원인은 red 테두리로 구분한다.
의미색은 red에 더해 하나(대개 해결·복구 green)까지다([shell.md](../blocks/shell.md) 색 절).

## 섹션으로 쓸 때

- 다른 패턴이 이끄는 페이지(상태 보고 등)에서 사건 하나의 원인을 물으면 원인 섹션 하나로 답한다.
- 추천 블록: 직접 원인 → 근본 원인을 이은 graph([diagram](../blocks/diagram.md)), 영향 그래프. 구도는 Canvas.

## 함께 자주 섞는 패턴

- 장애 회고에서 report(상태·영향·다음)·timeline(경위)·compare(대응 비교)와([recipes](../recipes.md)).

## explanation 쓰는 곳

- 원인 그래프 옆 열에 `constraint`(어떤 조건이 겹쳐야 사고가 되나), 타임라인 아래에 `reason`(왜 인지가 늦었나), 영향 그래프 옆에 `impact`. 원인을 어떻게 확인했는지는 evidence다.

## 추천 조합

요약(히어로 또는 요약 행) + 타임라인/status rail + evidence + before-after `fix` + checkpoint(원인 확정) + 재발 방지 checklist 담당 변형 + closing `takeaway`. 블록은 패턴이 소유하지 않는다. 다른 패턴 문서의 블록도 필요하면 그대로 빌린다([blocks.md](../blocks.md)).

## 페이지 주 패턴일 때 (자연스러운 깊이 4~6)

이 패턴이 페이지 대부분을 차지할 때의 출발점이다. 깊이는 참고값이고 섹션 수는 독자 질문이 정한다. 첫 화면 섹션은 그림이 필수이고, 그 아래 섹션은 핵심 구조가 있으면 그림을 권장한다. 아래를 전부 채우지 않는다.
영향·순서·원인·재발 방지는 서로 다른 독자 질문이므로 각각 섹션으로 두는 것이 기본이다. 영향과 순서를 한 그림이 함께 답하면 한 섹션으로 합친다.

header(h1 → 히어로 또는 요약 행: 발생 / 복구 / 영향 시간 → 요약 2~3문장) → ① 어디까지 닿았나: 영향 그래프(대상·범위·지속) → ② 무슨 순서로: 세로 타임라인(발생·인지·조치·복구) + 지속 시간 막대([timeline](../blocks/timeline.md) SVG 시간 막대 `data-variant="timebar"`) → ③ 왜: 직접 원인 vs 근본 원인 그림 → ④ 다시 안 생기게: 대응 한 줄 + checklist 담당 변형(`data-variant="owner"`, 그림 없음) → 문서 끝 closing `takeaway`(배운 점 하나 + 담당·기한 메타, [closing](../blocks/closing.md)).

- **시간을 머리에 둔다.** 시각이 있으면 h1 바로 아래 히어로 수치 1개(영향 시간, [hero](../blocks/hero.md)) 또는 요약 행 `발생 / 복구 / 영향`으로 쓴다. 요약 행 값은 데스크톱 한 줄(약 35자 이내).
- 요약은 2~3문장: 무슨 일, 누구에게, 지금 상태. 원인 분석은 ③으로 미룬다.
- 한 사실은 한 번: 히어로가 `영향 42분`이면 요약 행 `영향` 칸은 `주문 내보내기 실패`처럼 범위만 쓰고 시간은 되풀이하지 않는다.
- 직접 원인과 근본 원인을 한 문장에 섞지 않는다. 직접 원인 = 무엇이 방아쇠를 당겼나(설정 변경·트래픽 급증). 근본 원인 = 왜 그것이 막히지 않았나(검사 없음·경보 늦음).
- 대응은 이미 한 조치, 재발 방지는 앞으로 할 일이다. 섞지 않는다.

①은 첫 화면이라 그림 필수, ②·③은 순서·원인 구조라 그림을 권장한다. ④는 checklist 구조라 그림 없이 둔다. 기한이 일부 행에만 있으면 그 열을 빼고 설명 줄에 넣는다. 담당·기한이 모두 없으면 확인 방법(`코드로` / `눈으로`)을 메타로 둔다.

## 패턴 안티패턴

- 핵심 구조가 있는 섹션을 그림 없이 문단으로만 채우기, 질문 없이 추천 블록을 전부 채우기, 짧게 만들려고 이유·조건을 지우기.
- 사람 탓 서술(구조와 절차의 원인으로 쓴다). 담당자 이름을 원인 칸에 쓰기.
- 발생·복구 시각, 영향 범위 없음. 시간이 본문 깊이 묻힘.
- 직접 원인만 쓰고 근본 원인 없음, 또는 둘을 한 문장에 섞기.
- "주의하겠다"뿐인 재발 방지(담당·기한·확인 방법 없는 항목).

## 경계

- 결과·지표 정리가 목적이면 report, 사건 경위면 incident.
- 여러 사건을 기간으로 정리하면 timeline 변경 내역.

스토리라인(표지 다음 제목 목차는 공통이라 생략):
사건 → 영향 → 타임라인 → 근본 원인 → 왜 못 막았나 → 대응 → 재발 방지

| 장 | `data-kind` |
| --- | --- |
| 사건 | `cover`(h1 = 무슨 일이 왜 났나 한 문장, 요약 3행 `발생` / `복구` / `영향`) |
| 영향 | `stat`(영향 시간·범위 숫자 하나) 또는 `evidence`(영향 그래프) |
| 타임라인 | 근거(SVG 시간 막대 `data-variant="timebar"`, 발생·인지·조치·복구) |
| 근본 원인 | `breakdown`(직접 원인 → 근본 원인) |
| 왜 못 막았나 | `assertion`(빠진 방어선 한 문장) |
| 대응 | 근거 또는 `screenshot`(바뀐 경보·화면에 spotlight) |
| 재발 방지 | `closing`(`takeaway`: 지킬 것 + 담당·기한) |

Impact: 영향(`stat`), 왜 못 막았나(`assertion`).
