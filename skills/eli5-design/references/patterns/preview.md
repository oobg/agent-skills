# preview — 결과물 미리보기

**패턴: 받으면 어떤 모양이고, 무엇을 확인할 수 있나?** 페이지 타입이 아니라 이 질문에 답하는 섹션의 표현 방식이다. 다른 패턴 섹션과 한 페이지에 섞어 쓴다(섹션 `data-pattern="preview"`).

미리보기는 결과물이 아니라 검증 단계다. 독자는 읽고 나서 "더 볼 가치가 있나"를 판단할 수 있어야 한다.

## 이 패턴이 답하는 질문

- 이것은 무엇이고, 받으면 어떤 모양인가(파일·화면·표)?
- 여기서 무엇을 확인할 수 있고, 각 칸(열)은 무엇을 뜻하는가?
- 무엇이 포함되지 않는가? 실제와 무엇이 다를 수 있는가?
- 직접 보려면 어디로 가고, 다음은 무엇인가?

## 요청 신호

"결과물 어떻게 생겨", "엑셀 양식 미리보기", "출력 샘플", "받으면 뭐가 와", "리포트 양식", "화면 미리보기".

## 대표 도식

표 결과물은 미니 격자 썸네일(diagram grid) + 실물 같은 결과물 목업(tab-preview). 받는 화면이 있으면 [mockup-frame](../blocks/mockup-frame.md).
결과물이 표가 아니라 HTML·화면이면 번호 핀 해부도([diagram](../blocks/diagram.md) 핀 오버레이: 화면 와이어프레임 위 번호 핀 + 번호별 설명) + 파일 구성 도식(파일·폴더 관계를 그린 diagram graph)을 대표 도식으로 쓴다.
핀 해부도는 연동 동작이 기본이다. 범례 항목에 올리거나 Tab으로 가면 같은 번호 핀과 영역이 켜진다([diagram](../blocks/diagram.md) (g) pins).

화면 미리보기는 기기 프레임에 담는다. PC 화면은 노트북 창 프레임(`data-device="desktop"`), 모바일 화면은 폰 프레임(`data-device="mobile"`)이다([mockup-frame](../blocks/mockup-frame.md) 기기 변형).
둘 다 있으면 노트북 창을 크게, 폰을 옆에 작게 둔다. 프레임 없는 맨 화면 조각은 실제 화면으로 오해받는다.
- **정적 그림 축소 프레임.** mockup-frame의 375px 고정 폭·최소 높이는 iframe으로 실제 페이지를 넣을 때만이다. 기기 프레임을 정적 그림(SVG·미니 마크업) 둘레에 두르면
  폰 화면 폭 140~200px, 베젤 6px, 모서리 28px로 줄여도 된다. 비율(폭:높이 약 9:19.5)은 지킨다.

## 섹션으로 쓸 때

- 다른 패턴이 이끄는 페이지에서 "결과물은 어떻게 생겼나"가 질문 하나로 나오면 미리보기 섹션 하나로 답한다.
- 추천 블록: [tab-preview](../blocks/tab-preview.md), [mockup-frame](../blocks/mockup-frame.md) 기기 프레임, 핀 해부도([diagram](../blocks/diagram.md) (g)), [thumb-cards](../blocks/thumb-cards.md). 구도는 Canvas 또는 Spotlight.
- 범위 고지(`예시 데이터`·`미리보기`)는 섹션으로 쓸 때도 그림마다 둔다.

## 함께 자주 섞는 패턴

- 기능 소개의 첫 섹션으로 flow·compare·faq와([recipes](../recipes.md)), compare 시안 앞에서 "받으면 이렇게 보여요"로, report 결과·지표의 근거 화면으로.

## explanation 쓰는 곳

- 목업·해부도 아래에 `interpretation`(각 칸이 무엇을 뜻하나)과 `constraint`(실제와 다를 수 있는 점). 포함되지 않는 것은 explanation `exception` 또는 diff-rows 배지 행으로 쓴다.

## 추천 조합

기기 프레임 또는 핀 해부도 + tab-preview + explanation `interpretation`·`constraint` + closing `action`. 블록은 패턴이 소유하지 않는다. 다른 패턴 문서의 블록도 필요하면 그대로 빌린다([blocks.md](../blocks.md)).

## 페이지 주 패턴일 때 (자연스러운 깊이 3~5)

이 패턴이 페이지 대부분을 차지할 때의 출발점이다. 깊이는 참고값이고 섹션 수는 독자 질문이 정한다. 첫 화면 섹션은 그림이 필수이고, 그 아래 섹션은 핵심 구조가 있으면 그림을 권장한다. 아래를 전부 채우지 않는다.

header(문장형 리드: 무엇인지 한 문장) → ① 어떤 모습인가: 기기 프레임 화면, 또는 flow-line 한 줄 + 미니 격자 그림 카드(thumb-cards) → ② 확인할 수 있는 것: tab-preview(시트 탭 + 표 목업 + 열 주석) 또는 번호 핀 해부도 → ③ 포함되지 않는 것: 구조 블록(diff-rows 배지 행 또는 짧은 `ul` 행 3개 이내, 그림 없음) → 문서 끝 closing `action`(직접 보기·다음, [closing](../blocks/closing.md)).
  그림 없는 섹션은 구조 블록으로 짓는다(SKILL.md 원칙 4번). callout으로 두지 않는다.

- **범위 고지는 필수다.** 실제 환경과 다른 점을 ③ 또는 머리 바로 아래에 한 번 쓴다. 예: "여기서 바꾼 건 저장되지 않아요", "예시 데이터라 실제 숫자와 달라요", "결제 단계는 빠져 있어요".
- 포함되지 않는 것은 3개 이내 짧은 줄이다. 빠진 이유보다 독자가 기대하면 안 되는 것을 쓴다.
- 직접 보기·다음은 한 줄이다. 어디서 열고, 언제 실제가 되는지(또는 누구에게 물을지)만 쓴다.

`예시 데이터` 또는 `미리보기` 표시는 패턴 공통 규칙이다. tab-preview, 해부도, 목업 프레임, 썸네일 등 실제가 아닌 모양을 보여 주는 그림마다 하나씩 둔다.

색: 묶음마다 상태가 갈리면 카드마다 상태 배지 하나(`지금 가능` green / `준비 중` orange 등). 썸네일 격자와 표 목업은 머리 행 blue-light, 합계 blue(표는 blue-light + 2px blue 선)가 기본이다([shell.md](../blocks/shell.md) 색 절).

합성 예: "주문 내보내기 파일: 요약 시트와 상세 시트", 값은 `상품 1`, `팀 A`, 둥글지 않은 작은 합성 수치.

## 패턴 안티패턴

- 핵심 구조가 있는 섹션을 그림 없이 문단으로만 채우기, 질문 없이 추천 블록을 전부 채우기, 짧게 만들려고 이유·조건을 지우기.
- 범위 고지 없음. 미리보기와 실제 결과물의 구분이 없음.
- PC 화면을 폰 프레임에, 모바일 화면을 넓은 창에 담기. 프레임 없는 맨 화면 조각.
- 열 7개 초과(원칙 상한). 그 이상은 시트를 나눈다. 가로 스크롤이 생기면 실패다.
- 실제 개인 데이터처럼 보이는 값(실명·연락처·실제 상호).
- 열 의미 설명 없음.
- 회색만 있는 썸네일·표 목업, 상태가 갈리는데 배지를 숨겨 차이가 안 보이는 카드.
- 기능 홍보 문구로 채운 머리(무엇인지 대신 왜 좋은지).

## 경계

- preview는 결과물의 **모양**, report는 그 결과물로 **알게 된 것**.
- 쓰는 법을 단계로 따라가게 하려면 guide.

## 덱으로 낼 때

Deck Type **Demo**(제품이 쓰이는 장면) 또는 **Explainer**(결과물의 모양): `<main class="d0-deck" data-pattern="preview">`. 규칙은 [deck](../output/deck.md).

Demo 스토리라인(표지 다음 제목 목차는 공통이라 생략):
상황 → 사용자 → Before → 제품 → 사용 흐름 → 실제 화면 → After → 다음

| 장 | `data-kind` |
| --- | --- |
| 상황 | `cover`(h1 = 무엇이 달라지나 한 문장) |
| 사용자 | 근거(누가 어디서 쓰는지 그림 + 요점) |
| Before | `screenshot`(지금 화면, 막히는 곳 spotlight) 또는 `evidence` |
| 제품 | `assertion`(한 문장 정의) |
| 사용 흐름 | 근거(단계 도식) |
| 실제 화면 | `screenshot`(봐야 할 곳 spotlight + 번호 주석) |
| After | `stat` 또는 `evidence`(전/후) |
| 다음 | `closing`(`action`: 써 볼 사람·도입 요청) |

Impact: 제품(`assertion`), After(`stat`).
Explainer로 결과물 모양만 보이면 결과물 한 문장(`cover`) → 전체 모양(근거) → 해부(`screenshot` 또는 diagram 핀) → 예시 값(`evidence`) → 다음(`closing` `action`)로 줄인다.
