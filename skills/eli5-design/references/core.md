# core — 모든 결과물에 적용하는 규칙

page·deck과 레시피에 상관없이 지킨다. 아래 다섯 문장이 이 스킬의 규칙 전부이고, 나머지 문서는 이 다섯을 구현하는 방법이다.

## 다섯 규칙

1. **그림·표·글은 서로 다른 정보를 맡는다.** 이미 보여 준 내용을 카드·캡션·요약으로 반복하지 않고, 추가 정보가 없으면 제거한다.
2. **비교는 공통 요소를 같은 시각 문법으로 그리고 실제 차이만 바꾼다.** 역할이 모호한 요소와 없음·미확정 같은 부재 상태는 그림 안에서 직접 밝힌다.
3. **주어진 사실을 바꾸거나 없는 사실·수치를 만들지 않는다.**
4. **도식화가 최우선이다.** 설명은 그림(라벨·구절·핀·같은 틀 비교)으로 최대한 하고, 그림으로 안 되는 이유·조건만 한 줄로 쓴다.
5. **사용자에게 보이는 결과에는 내부 구현 식별자와 제작·판정 과정을 드러내지 않고,** 완성 후 실제 렌더를 보며 다시 편집한다.

## 1. 서로 다른 정보

- 그림마다 "이 그림을 지우면 독자가 무엇을 모르게 되나"를 한 문장으로 답할 수 있어야 한다. 답이 없으면 장식이니 지운다. 대상과 무관한 클립아트, 제목 곁 아이콘, 관계 없이 명사를 아이콘으로 바꿔 늘어놓은 그림이 여기에 든다. 비유 사물이 포함·연결·순서를 싣고 있으면 장식이 아니다.
- 그림이 단계·관계·순서를 이미 보여 주면 같은 단계를 카드·열·목록으로 다시 만들지 않는다. 캡션은 그림 속 순서를 문장으로 다시 읽지 않고, 그림이 못 보여 주는 이유·조건이 있을 때만 쓴다. 더할 말이 없으면 비운다.
- 마지막 요약 카드나 되짚기 장은 앞에서 본 내용을 다시 말할 뿐이면 두지 않는다.
- 글로 충분한 내용에 그림을 억지로 붙이지 않는다. 그림이 없는 섹션도 된다. 그림은 개수가 아니라 대신 설명하는 정보량으로 센다.
- 같은 숫자·결정 문구는 필요한 곳에서 반복해도 된다(제목·근거·결정 요청에 되풀이되는 `팀 A부터 적용` 같은 문구). 반복이 지나친지는 렌더를 보고 판단한다.

## 2. 비교와 직접 라벨

- 비교하는 양쪽은 같은 틀 크기·좌표계·순서·축척·모양을 쓰고, 주장한 차이만 다르게 그린다. 그리는 방식이 달라 구조 차이와 드로잉 차이가 섞이면 비교가 안 된다.
- 모양만으로 뜻을 알 수 없는 노드·점선·빈칸·채움은 그 자리 곁에 직접 라벨을 단다(반복되면 그림 안 작은 범례). 캡션에만 적지 않는다.
- 한쪽에 없는 항목은 대응하는 자리를 비워 두고 `없음`, `미확정`, `내년 예정(미확정)`처럼 실제 상태를 글자로 적는다. 점선이나 빈칸만으로 없음을 말하지 않는다. 표에서도 칸을 비우지 않는다.

## 3. 사실

- 사용자 입력에 없는 단계·사실·수치·이름·날짜·출처를 그림에도 글에도 보태지 않는다. 계산한 값(합·차이·평균·비율)은 입력에서 계산하고, 막대 길이도 값에서 계산한다.
- 해석이 갈리면 사용자에게 확인한다. 확인할 수 없으면 가장 합리적인 해석을 쓰고 그 가정을 결과 보고에 남긴다.
- 적용 전 수치는 `예상치`로 표시하고 측정값과 섞지 않는다. 출처가 없으면 출처 줄을 만들지 않는다.
- 예시 데이터는 전부 합성이다. 실제 회사·제품·사람·티켓 번호처럼 보이는 값, 외부 사이트 링크를 넣지 않는다.

## 4. 짧은 글과 용어

- 글로 쓰려던 것은 먼저 그림 라벨·선 위 구절·번호 핀·같은 틀 비교로 올린다. 남는 이유·조건만 라벨 하나 아래 한 줄이고, 한 줄로 안 되면 질문이 둘이니 나눈다. 라벨 없는 문단을 늘어놓지 않는다.
- 용어의 비유는 생김새 하나(아이콘)가 아니라 그 사물이 일하는 장면으로 그린다(쿠키 틀 하나에서 같은 쿠키 여럿이 나오고 틀은 그대로 남음, 뚜껑 연 상자와 그 안에 든 것, 번호표를 쥔 사람들의 줄). 사물은 노드·틀이 아니라 면과 부분으로 그린 삽화다([diagrams/index.md](diagrams/index.md) 예시). 장면으로 그릴 수 없는 것만 원·점으로 둔다. 글은 처음 나오는 곳에서 그 비유를 한 번 잇는다(`<abbr title>` 또는 괄호). 뒤 섹션에서야 풀지 않는다.
- 비유는 독자가 실제로 쓰는 물건·장면(택배 상자, 대기 번호표)이다. 영어 관용구를 옮긴 은유는 비유가 아니다.

## 5. 독자에게 보이는 말과 마지막 편집

- 이 스킬의 내부 이름(레시피·블록·게이트·토큰 같은 말, `data-*` 값, 영문 블록 이름, 파일 이름)을 화면에 내지 않는다. 사용자 요청 원문이 그 낱말을 주제로 쓰면 된다. 원문을 옮긴 글은 `q`·`blockquote`나 `data-verbatim`으로 감싼다.
- `날짜가 없어서 절차로 그렸어요`처럼 문서를 만든 이유를 독자에게 설명하지 않는다. 결과를 이해하는 데 필요한 이유만 남긴다.
- 완성하면 [final-review.md](final-review.md)의 네 질문으로 렌더를 보고 고친다.

## 말투와 문장

- page는 해요체, deck은 제목·본문·해석을 `-다`체로 쓰고 섞지 않는다. 사용자가 준 문구·인용, deck 마지막 장의 요청(`정해 주세요`), 네비 안내 같은 UI 문구는 그대로 둔다.
- 누가·무엇을·어떻게를 일상 문장으로 쓰고, 원인 → 결과 순서로 푼다. 아래 직역투는 고친다.

| 직역투 | 예 | 고친 방향 |
| --- | --- | --- |
| 영어식 은유 | 방아쇠, 판을 바꾸다, 빙산의 일각 | 실제로 일어난 일을 동사로 쓴다 |
| 무생물 주어 + 의지 동사 | `설정이 배포를 멈춘다` | 사람·시스템을 주어로 두거나 조건절로 푼다 |
| 압축 대구 | `A는 B, C는 D` | 두 사실의 관계(그래서·함께·그 뒤에)를 이어 쓴다 |
| 분열문 | `중요한 것은 순서다` | 주어와 서술어를 바로 잇는다 |
| 번역 조사 | `~에 의해`, `~를 통해`, `~에 있어서` | 능동문, `~로`, `~에서` |
| 모호한 조건 | `~가 빠지면` | `설정되지 않으면`, `0이 되면`처럼 구체적으로 |

- 문장이 두 개 이상이고 역할이 다르면 `<span class="d0-sentence">`로 문장마다 줄을 나눌 수 있다. `<br>`을 늘어놓지 않는다.

## 보이는 모양의 기본

- 시각 언어는 형제 스킬 day0-design의 토큰을 따른다. 토큰·정본 CSS·JS는 `scripts/inline_assets.py`가 채우므로 읽지 않는다. 라이트 온리이고 다크 팔레트를 만들지 않는다.
- 강조 순서는 크기 → 위치 → 여백 → 무게 → 색이다. blue는 메인이자 그 장면의 초점 하나에 쓰고, 삽화 사물은 실물이 그 색일 때만 Day0 포인트 색(green·red·orange)으로 칠하고(사과는 red) 나머지는 회색이다. 한 결정에 두 지표가 함께 필요하면(처리량과 오류율) 둘을 같은 문법으로 나란히 두고 강조해도 된다.
- green·red·orange는 상태 표식에서 의미색(green 완료·통과, orange 주의, red 위험·실패)이고 글자 색으로 쓰지 않는다. 사물 색과 헷갈리지 않게 상태는 색만으로 말하지 않고 글자나 모양을 함께 둔다.
- 그라디언트·글래스·두꺼운 그림자·3D·사람 일러스트를 쓰지 않는다. 텍스트 상자를 화살표로 이은 것은 도식이 아니다.
- 구조는 시맨틱 태그(`section`·`figure`·`ol`·`dl`·`table`·`time`·`data`·`details`)로 짓고, 헤딩은 h1 → h2 → h3, 정보 SVG는 `role="img"` + `<title>`이다. 접근성 하한은 WCAG 2.2 AA다.
