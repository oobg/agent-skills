# writing — 글쓰기·개행 규칙

문구를 쓰고 확정하는 규칙이다: 용어 풀이, 한 사실은 한 번(원칙 8번), 개행 규칙, 직역투 점검. page·deck 공통이다.

## 용어 풀이 (원칙 6번)

- 본문 설명은 라벨을 단 [explanation](blocks/explanation.md) 블록으로 쓰고 한 라벨 아래 1~3문장이다(4문장 이상이면 질문을 나눈다). 라벨 없는 문단을 늘어놓지 않는다.
- 용어는 일상 사물에 빗댄다. 용어는 **처음 나오는 곳**(대개 header 요약 행이나 리드)에서 `<abbr title>` 또는 괄호 속 짧은 비유로 푼다. 뒤 섹션에서만 풀지 않는다.
- 용어 풀이는 `abbr` 또는 괄호 중 하나만 처음 등장 시 1회다.

## 한 사실은 한 번 (원칙 8번)

- 숫자·결정은 정본 위치 하나에만 본문으로 둔다. 같은 숫자 문자열(예 `26분`)은 화면에 보이는 텍스트에 페이지당 2회 이하다.
  세는 범위는 `body.innerText`다(SVG `<text>`는 이미 들어 있으므로 따로 더하지 않고, SVG `<title>`·`<desc>`는 들어 있지 않아 세지 않는다).
- closing 메타(`dl.d0-closing__meta`·`dl.d0-slide__meta`)와 덱 제목 목차는 앞 사실을 가리키는 자리라 빼고 센다. 결정은 요약 행 또는 할 일 중 한 곳에 두고 다른 곳은 짧은 참조만 쓴다.
- 요약 행 값은 데스크톱 한 줄(약 35자 이내, [header.md](blocks/header.md) 요약 행).
- **중복 제거는 맥락 제거가 아니다.** 같은 숫자·결정을 되풀이하지 말라는 규칙이지, 그 숫자가 왜 나왔는지·무엇을 뜻하는지·어떤 조건에서 달라지는지를 지우라는 규칙이 아니다.
  그림이 이미 보여 준 모양은 글로 반복하지 않고, 그림이 보여 줄 수 없는 이유·조건·영향은 explanation, 근거는 evidence로 남긴다.

## 개행 규칙

설명 문단이 옆 공간이 남는데도 일찍 줄 바뀌는 버그를 막는다. 원인은 대개 리드나
설명 `p`에 컨테이너보다 좁은 `max-width`(px·`ch`)를 건 것이다.
`day0-design/references/anti-patterns.md`가 슬롭 신호로 꼽는 좁은 부제와 같은 문제다.

- 리드·섹션 설명·블록 설명 문단(explanation `dd` 포함)은 **부모 컨테이너 폭을 그대로 쓴다.**
- 컨테이너보다 좁은 `max-width`·`width`·`ch` 단위를 `p`에 걸지 않는다. 좁혀야 하면 블록 컨테이너를 좁힌다. 줄이 길면 페이지 전체를 `data-width="narrow"`로 둔다([shell.md](blocks/shell.md) 줄 길이 절).
- 한글은 `word-break: keep-all`, 본문은 `text-wrap: pretty`.
- `text-wrap: balance`는 제목 셀렉터(h1~h3)에만 쓴다.
- **문장 단위 개행(선택).** 기본은 이어 쓰기다. 리드·설명이 2문장 이상이고 데스크톱 폭에서 2줄을 넘기거나,
  문장마다 역할이 다르면(예: "무엇을 바꿨나" / "지금 상태·부탁") 온점 단위로 문장마다 줄을 나눈다.
  문장마다 `<span class="d0-sentence">`(`display: block`) 또는 별도 `<p>`를 쓰고 `<br>`을 늘어놓지 않는다.
  한 문장이 한 줄을 넘치면 그 안에서는 자연 줄바꿈한다.
- **요약 행.** 리드 내용이 "이전 → 현재 → 요청"처럼 역할로 나뉘면 문단 대신 header 요약 행(`라벨 | 한 문장` 2~3행)을 쓴다.
  compare 전/후·결정 변형, report, incident, timeline 변경 내역이 첫 섹션일 때의 기본 리드다. 결정·요청 행(`data-tone="decision"`)이 있으면 결정 callout과 closing `decision`을 두지 않는다.
  결정이 둘 이상이면 `결정 필요` 칸에 짧은 `ol`(최대 2개), 셋 이상이면 가장 중요한 1개만 요약 행에 두고 나머지는
  할 일 목록으로 보낸다. 요약 행은 최대 3행이다. 행 라벨·두 번째 결정의 세부 규칙은 [header.md](blocks/header.md)가 정본이다.

## 직역투 점검

한글로 썼다고 다 쉬운 풀이가 아니다. 영어 문장 구조나 영어식 비유를 그대로 옮긴 문장은 낱말이 쉬워도 한 번에 읽히지 않는다.
문구를 확정하기 전에(SKILL.md 작업 순서 8번) page·deck 모두 이 목록으로 한 번 읽는다. 범위는 제목·리드·라벨·설명·캡션·해석 줄·SVG `<text>`·closing 메타·버튼 문구까지 화면에 보이는 모든 글이다.

### 고칠 방향

- **누가·무엇을·어떻게**를 일상 문장으로 쓴다. 주어가 사람이나 시스템이면 그대로 밝히고, 조건은 조건절로 푼다.
- **원인 → 결과** 순서로 푼다. 결과를 먼저 압축해 놓고 원인을 뒤에 붙이지 않는다.
- **비유는 용어 풀이용 일상 사물만** 쓴다(원칙 6번 "용어는 비유로 푼다", 위 용어 풀이 절). 독자가 실제로 쓰는 물건·장면(택배 상자, 대기 번호표)이어야 하고, 영어 관용구를 옮긴 은유는 비유가 아니다.
- 말투는 출력 형식을 따른다(page 해요체, deck `-다`체). 아래 예시는 page 문장이다.

### 점검 목록

| 직역투 | 알아보는 법 | 고친 방향 |
| --- | --- | --- |
| 영어식 은유 | 방아쇠, 키운 것, 문을 열다, 게임 체인저, 판을 바꾸다, 빙산의 일각 | 실제로 일어난 일을 동사로 쓴다 |
| 무생물 주어 + 의지 동사 | `설정이 배포를 멈춘다`, `오류가 팀을 괴롭힌다` | 사람·시스템을 주어로 두거나 조건절로 푼다 |
| `A는 B, C는 D` 압축 대구 | 두 사실을 쉼표 하나로 맞붙여 표어처럼 만든 문장 | 두 사실의 관계(그래서·함께·그 뒤에)를 이어 쓴다 |
| `~하는 것은 ~이다` 분열문 | `중요한 것은 순서다`, `키운 것은 경보다` | 주어와 서술어를 바로 잇는다 |
| 번역 조사·동사 | `~을 가지다`, `~에 의해`, `~에 대해`, `~를 통해`, `~에 있어서` | `~이 있다`, 능동문, `~을`·`~로` |
| 명사 나열 압축 | `빠진 검사와 경보`처럼 무엇이 왜 빠졌는지가 수식어 하나에 눌린 구 | 무엇이 어떻게 됐는지 절로 푼다 |
| 주체·조건이 모호한 조건절 | `~가 빠지면`(누가 빼나, 값이 없나, 줄었나) | 조건을 구체적으로 쓴다(`설정되지 않으면`, `0이 되면`) |

### 예시 쌍

| 직역투 | 풀어 쓴 문장 |
| --- | --- |
| 방아쇠는 설정 정리, 키운 것은 빠진 검사와 경보예요. | 설정을 정리하면서 제외되었던 검사와 경보도 함께 보강했어요. |
| 이제 작업자 수가 빠지면 배포가 멈춰요. | 이제 워커 수가 설정되지 않으면 배포되지 않아요. |

첫 문장은 영어식 은유(방아쇠·키운 것) + 압축 대구 + 명사 나열 압축이 겹쳤다. 둘째 문장은 주체·조건이 모호한 조건절(`빠지면`)과 무생물 주어(`배포가 멈춰요`)다.
용어는 독자가 화면에서 실제로 보는 말(`워커`)을 쓰고, 처음 나올 때 괄호 속 짧은 비유로 푼다.
