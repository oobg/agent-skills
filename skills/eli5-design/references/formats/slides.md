# slides — 발표용 슬라이드

독자가 알고 싶은 것: 그래서 결론이 뭐고, 왜 그렇게 말할 수 있으며, 나는 무엇을 하면 되지?
읽고 나서 할 수 있어야 하는 것: **한 장씩 따라오며 결론에 동의하고 결정·행동한다.**

문서형 페이지와 다른 점은 셋이다. 한 슬라이드에 메시지 하나, 슬라이드끼리 이어지는 인과(스토리라인),
발표나 화면 공유로 한 장씩 넘기며 보는 쓰임이다. 그래서 문서형 섹션 상한(2~4개)과 첫 화면 규칙 대신
덱 규칙을 따른다(정본: [slide-deck](../blocks/slide-deck.md) 덱 게이트).

## 독자가 다 읽고 답할 수 있어야 할 질문

- 첫 장만 봐도 현재 상태, 문제, 결정할 것을 아는가?
- 슬라이드 제목만 이어 읽어도 하나의 이야기(주장 → 근거 → 할 일)가 되는가?
- 각 주장의 근거는 무엇이고, 그 근거에서 무엇을 읽어야 하는가?
- 그래서 누가 언제까지 무엇을 하는가?

## 요청 신호

"발표 자료", "슬라이드로", "장표", "덱 만들어줘", "화면 공유용", "보고 발표", "제안 발표", "기술 발표".

## 변형

`<main class="d0-deck" data-variant="...">`로 표시한다. 이름표일 뿐 스타일은 바꾸지 않는다.
공통 뼈대는 **왜 이 얘기를 하는가 → 무슨 문제 → 데이터가 보여 주는 것 → 알아낸 것 → 그래서 할 일 → 언제 어떻게**다.

| 변형 | 언제 | 슬라이드 순서(출발점) |
| --- | --- | --- |
| 업무 보고 `report` | 진행 상태·결과를 발표로 보고한다 | 요약 → 현재 상태 → 핵심 성과 → 문제·리스크 → 원인 → 대응 → 다음 일정 |
| 제안 `proposal` | 기능·사업을 제안하거나 제품을 소개한다 | 문제 → 사용자 영향 → 원인 → 해결 방향 → 제안 → 화면·흐름 → 범위 → 예상 효과 → 리스크 → 다음 단계 |
| 전략 `strategy` | 방향을 고르고 실행 과제를 정한다 | 요약 → 상황 → 핵심 문제 → 왜 지금 → 원인 → 분석 → 선택지 → 추천 → 실행 과제 → 로드맵 → 기대 효과 |
| 기술 발표 `tech` | 구조 변경·성능 개선을 설명한다 | 문제 → 기존 구조 → 병목 → 측정 결과 → 선택지 → 선택 기준 → 변경 구조 → 구현 → 전/후 → 트레이드오프 → 다음 단계 |

제품 소개 제안은 한 문장 정의 → 문제 → 기존 방식의 한계 → 해결 방식 → 핵심 기능 → 사용 흐름 → 화면 → 차별점 → 도입 → 요청 순서로 바꾼다.
순서의 항목 수가 슬라이드 상한(12)을 넘으면 두 항목을 한 장에 묶지 말고, 독자 질문에 덜 필요한 항목을 뺀다.

## 권장 구성 (슬라이드 5~12장, 표지·제목 목차 포함)

권장 구성은 출발점이다. 독자 질문에 필요한 슬라이드만 만든다.

1. **표지 = 결론.** h1은 덱 전체의 결론 문장이다. 아래에 요약 3행(`현재 상태` / `문제` / `결정할 것`)을 둔다. 그림은 없어도 된다.
2. **제목 목차.** 모든 슬라이드의 액션 타이틀을 순서대로 나열한 `ol`이다. 항목은 해당 슬라이드로 가는 링크다.
   이 목록만 읽고 논리가 이어지지 않으면 슬라이드를 고치기 전에 제목부터 고친다.
3. **본 슬라이드.** 한 장 = 주장 하나 = 근거 그림 하나 = 해석 또는 출처 한 줄. 변형 표 순서를 따른다.
4. **핵심 수치 슬라이드(선택).** 결론 숫자가 있으면 숫자 하나를 크게 + 라벨 + 증감 한 줄로 한 장을 쓴다. 문서형의 히어로 자리를 이 슬라이드가 대신한다.
5. **마지막 장 = 할 일.** 누가, 언제까지, 무엇을. 3행 이내 목록이고, 그림 대신 요약으로 둘 수 있다(요약 예외).

슬라이드 하나의 해부는 결론 제목(+ 보조 한 줄) → 근거(차트·도식·화면 와이어 하나) → 해석 또는 출처 한 줄이다.
읽는 순서는 주장 → 증거 → 해석이다.
근거 슬라이드의 기본 배치는 **그림 + 요점 나란히(split)**다. 왼쪽에 근거 그림, 오른쪽에 그 그림에서 읽을 요점 2~3개를 둔다.
그림만 전체 폭으로 두면 SVG 최대 폭 제한 때문에 무대 좌우가 비므로, 전체 폭 그림은 가로로 긴 도식처럼 그림이 무대 폭을 채울 때만 쓰는 예외다.

합성 예: "알림 개편 3분기 업무 보고(`report`)", "주문 내보내기 예약 기능 제안(`proposal`)", "내보내기 처리 구조 변경 기술 발표(`tech`)".

## 대표 도식

슬라이드마다 그 주장의 근거 그림 하나다. [diagram](../blocks/diagram.md)의 막대·연결 그래프·단계·화면 와이어를 쓴다.

- 데이터는 근거다. 차트 위에 결론 문장(액션 타이틀)이 있고, 강조할 계열 하나만 blue, 나머지는 grey다.
- 축 눈금·범례·격자선은 읽는 데 필요한 것만 남긴다. 값 라벨을 막대 끝에 달면 범례와 눈금을 지운다.
- 전/후는 막대 두 개, 구조는 연결 그래프, 순서는 단계 도식, 화면은 와이어프레임이다.
- 핵심 수치 슬라이드는 큰 숫자 자체가 그림이다.

## 문장 규칙

- **액션 타이틀.** 제목은 명사가 아니라 결론 문장이다. 서술어(`-다`, `-요`, `-했다`, `-한다`)로 끝난다.
  `시장 규모` ✕ → `혼자 쓰는 팀이 이미 절반을 넘었다` ○. `현황`, `개요`, `분석 결과`, `Q&A` 같은 명사 제목은 실패다.
- 제목은 한두 줄(데스크톱 슬라이드 기준 약 40자 이내)이다. 넘으면 보조 한 줄로 나눈다.
- 보조 한 줄은 제목을 되풀이하지 않고 범위·조건을 더한다(`지난 8주, 팀 A 기준`).
- 본문은 슬라이드당 3줄, 불릿 3개까지다. 문단을 붙이지 않는다. 남는 말은 발표자가 말로 한다.
- 해석 줄은 "그래서 무엇을 뜻하나" 한 문장, 출처 줄은 `출처: 내부 집계(합성)`처럼 짧게 쓴다.
- 용어는 처음 나오는 슬라이드에서 괄호 속 짧은 비유로 푼다.
- 위계는 장식이 아니라 크기·위치·간격·정렬로 만든다.

## 프리셋 안티패턴

- 명사 제목만 있는 덱(`배경`, `현황`, `결론`). 제목 목차를 읽어도 이야기가 안 된다.
- 한 슬라이드에 문제·기능·장점·화면·성과·일정을 전부 넣기.
- 문서를 붙인 덱: 여러 줄 문단, 불릿 4개 이상, 표 전체 붙여 넣기.
- 의미 없는 아이콘·도형·그라디언트·3D·사람 일러스트, 모든 계열을 다른 색으로 칠한 차트.
- 그래프만 있고 결론 문장이 없음, 결론과 그래프가 다른 말을 함.
- 좁은 그림 하나만 전체 폭 무대에 올려 좌우가 빈 근거 슬라이드(기본은 그림 + 요점 split).
- 표지가 제목·날짜뿐이라 첫 장만 보고는 결정할 것을 모름.
- 슬라이드 13장 이상(나누거나 독자 질문에 덜 필요한 장을 뺀다).

## 경계

- 발표·화면 공유로 한 장씩 넘기며 설득하면 slides, 혼자 읽는 문서면 report.
- 옵션을 나란히 놓고 고르는 문서면 compare다. 발표 중 선택지 한 장은 slides 안의 슬라이드로 둔다.
- 흐름을 이해시키는 한 장짜리 설명이면 flow, 그 흐름을 근거로 무엇을 하자고 설득하면 slides.
- 날짜 순서가 주인공인 일정표면 timeline, 로드맵은 strategy 변형의 한 장으로 둔다.
