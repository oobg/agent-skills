# timeline — 일정·변경 내역

독자는 읽고 나서 시간과 의존성을 공유할 수 있어야 한다. 날짜보다 단계가 먼저다.

## 독자가 다 읽고 답할 수 있어야 할 질문

- 로드맵: 목표는 무엇이고, 지금은 어느 단계인가? 무엇이 언제 끝나고, 무엇이 끝나야 다음이 가능한가? 무엇이 일정을 흔드는가?
- 변경 내역: 언제 무엇이 바뀌었고, **나에게** 무엇이 달라지는가?

## 요청 신호

"로드맵", "일정표", "마일스톤", "언제 나와", "릴리스 노트 쉽게", "변경 내역", "업데이트 정리".

## 변형

| 변형 | 방향 | 구성 |
| --- | --- | --- |
| 로드맵 `roadmap` | 미래 | 목표 → 현재 단계 → 단계 흐름(상태 함께) → 마일스톤(목표일) → 의존성 → 위험 |
| 변경 내역 `changelog` | 과거 | 날짜·태그·항목, 항목마다 "당신에게 달라지는 점" |

변경 내역 변형은 일반 구조 기반이다. 외부 사례 근거가 약하므로 구성은 출발점으로만 쓴다.

## 대표 도식

- 로드맵: 단계 흐름([diagram](../blocks/diagram.md) steps). 단계는 탐색 → 설계 → 개발 → 미리보기 → 정식처럼 실제 상태 이름으로 쓰고, 단계마다 상태(완료·진행·예정)를 붙인다. 지금 단계 하나만 blue로 켠다.
- 의존성은 같은 그림 안의 화살표다. "A 완료 → B 가능"을 별도 목록이 아니라 단계·마일스톤 사이 화살표로 그리고, 막힌 화살표 하나만 강조한다. 단계 밖 의존(다른 팀·외부 승인)은 diagram graph로 따로 그린다.
- 마일스톤 목표일과 기간 길이가 중요하면 [timeline](../blocks/timeline.md)의 SVG 시간 막대(`data-variant="timebar"`)를 쓴다. 오늘 표식을 둔다.
- 변경 내역: 세로 timeline(`data-variant="vertical"`). 미커밋·예정 구간은 점을 나누지 않고 한 점(또는 한 구간)으로 묶어 배지 예산을 지킨다.

## 권장 구성 (섹션 2~4개, 앞쪽 핵심 섹션은 그림 필수)

권장 구성은 출발점이다. 독자 질문에 필요한 섹션만 만든다.

- 로드맵: header(문장형 리드 = 목표 한 문장 → 요약 행: 현재 단계 / 다음 마일스톤 / 목표일) → ① 지금 어디쯤: 단계 흐름 + 의존 화살표 → ② 언제 끝나나: 시간 막대(마일스톤 3~5, 오늘 표식) → ③ 무엇이 흔드나: 위험 checklist(그림 없음, 위험마다 영향 단계 하나).
- 변경 내역: header(요약 행: 이전 / 현재 / 달라지는 점) → ① 언제 무엇이: 세로 timeline → ② 무엇이 바뀌었나: 와이어프레임 전/후 + diff-rows.

요약 행 값은 데스크톱 한 줄(약 35자 이내). 결정이 둘 이상이면 [header.md](../blocks/header.md) 요약 행 규칙을 따른다.

- 현재 단계는 한 사실이다. 요약 행에 쓰면 그림에서는 표식으로만 보이고 문장으로 되풀이하지 않는다.
- 목표일이 확정이 아니면 `목표`라고 붙인다. 확정 날짜처럼 쓰지 않는다.
- 위험은 3개 이내다. "늦어질 수 있음"이 아니라 무엇이 늦으면 어느 단계가 밀리는지 쓴다.

합성 예: "알림 설정 개편: 설계 단계, 미리보기 목표 3월 둘째 주".

## 프리셋 안티패턴

- 그림 없이 글 블록만 쌓기, 권장 구성의 블록을 전부 채운 5개 이상 섹션.
- 날짜만 늘어놓고 단계·상태가 없음. 지금 어디쯤인지 안 보임.
- 의존성을 글 목록으로만 쓰기(그림에 화살표가 없음).
- 점 수십 개(원칙상 마일스톤 5개 이내, 더 있으면 기간으로 묶는다).
- 날짜 없는 마일스톤, 목표일과 확정일 구분 없음.
- 내부 용어·파일명·작업 번호 나열(독자에게 달라지는 점이 없음).

## 경계

- 날짜·목표일이 있으면 timeline, 순서만 있으면 flow.
- 장애 하나의 경위면 incident.

## 덱으로 낼 때

덱은 덜 맞는다. 날짜 순서는 한 장에 펼친 시간 막대에서 가장 잘 보이고, 넘기면 전체 길이와 겹침이 끊긴다. 기본은 page다.
로드맵을 발표해야 하면 report `proposal` 덱 안에 시간 막대 한 장으로 빌리는 쪽이 먼저다.
단독으로 낸다면 `<main class="d0-deck" data-preset="timeline" data-variant="roadmap">`, 규칙은 [deck](../output/deck.md).

스토리라인(5~6장, 표지 다음 제목 목차는 공통이라 생략):
지금 어디 → 전체 일정 → 위험 구간 → 의존성 → 다음 마일스톤

| 장 | `data-kind` |
| --- | --- |
| 지금 어디 | `cover`(h1 = 목표일에 맞는지 한 문장) |
| 전체 일정 | 근거(SVG 시간 막대 `data-variant="timebar"`, 전체 폭, 오늘 표식) |
| 위험 구간 | `evidence`(밀린 구간만 blue) |
| 의존성 | `breakdown`(선행 작업 → 막히는 작업) |
| 다음 마일스톤 | `summary`(결정·요청 한 가지) |

Impact: 목표일이나 남은 기간 숫자 하나(`stat`). 변경 내역 `changelog`는 덱으로 내지 않는다.
