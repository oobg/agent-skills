# deck — 한 장씩 넘기는 발표 덱 출력

출력 형식은 두 가지다. 기본은 한 장짜리 페이지(`page`)이고, 이 파일은 한 장씩 넘기는 발표 덱(`deck`) 규칙이다.
내용 프리셋(compare·flow·preview·report·guide·timeline·incident·faq)이 **무엇을 말할지** 정하고, 출력 형식은 **어떻게 보여 줄지** 정한다.
덱도 프리셋 하나를 고르고, 그 프리셋 파일의 독자 질문과 "덱으로 낼 때" 스토리라인을 따른다.

마크업·CSS·JS(16:9 한 장 보기, 네비, 키보드, 인쇄, 좁은 화면)와 크기 게이트의 정본은 [slide-deck](../blocks/slide-deck.md)다.
구도·강조 3단계·밀도 리듬은 [composition](../composition.md)이 정본이다. 이 파일은 덱의 구성과 의미 검사를 정한다.

## 언제 deck인가

- 요청 신호: "발표 자료", "슬라이드로", "장표", "덱 만들어줘", "화면 공유용", "한 장씩 넘기며", "보고 발표", "제안 발표", "기술 발표", "쉽게 보는 발표 슬라이드".
- 발표나 화면 공유로 한 장씩 따라오게 하면 deck, 혼자 읽는 문서면 page다. 신호가 없으면 page다.
- 출력 형식은 프리셋을 바꾸지 않는다. 옵션을 고르는 발표는 compare deck, 흐름을 설명하는 발표는 flow deck이다.

## 독자가 다 보고 답할 수 있어야 할 질문 (덱 공통)

프리셋의 독자 질문에 아래를 더한다.

- 첫 장만 봐도 결론과 결정할 것을 아는가?
- 슬라이드 제목만 이어 읽어도 하나의 이야기(주장 → 근거 → 할 일)가 되는가?
- 각 주장의 근거는 무엇이고, 그 근거에서 무엇을 읽어야 하는가?
- 그래서 누가 언제까지 무엇을 하는가?

## 루트 마크업

```html
<main class="d0-deck" data-preset="report" data-variant="status">
```

- `data-preset`은 필수이고 내용 프리셋 8개 중 하나다.
- `data-variant`는 그 프리셋의 기존 변형 이름표다(SKILL.md 이름표 목록). 변형이 없는 프리셋이면 생략한다.
- 둘 다 이름표일 뿐 스타일을 바꾸지 않는다. 슬라이드 마크업은 [slide-deck](../blocks/slide-deck.md)을 따른다.

## Deck Type과 프리셋

Deck Type은 덱의 쓰임을 부르는 문서용 이름이다. 속성으로 쓰지 않고, 루트에는 프리셋과 변형만 단다.

| Deck Type | 프리셋(변형) | 언제 |
| --- | --- | --- |
| Decision | compare `decision` | 선택지를 놓고 결정을 받는다 |
| Proposal | report `proposal` | 아직 적용 전인 변경·기능을 제안한다 |
| Executive Update | report `status`·`executive` | 진행 상태와 리스크를 위로 보고한다 |
| Explainer | flow, preview | 구조·흐름이나 결과물을 이해시킨다 |
| Demo | preview, guide | 제품이 쓰이는 장면을 보여 준다 |
| Retrospective | incident | 사건을 돌아보고 재발을 막는다 |

장마다의 순서(스토리라인)는 각 프리셋 파일의 "덱으로 낼 때" 절이 출발점이다.
순서의 항목 수가 12장을 넘으면 두 항목을 한 장에 묶지 말고 독자 질문에 덜 필요한 항목을 뺀다.

### 폐기된 slides 변형

예전 slides 전용 변형 이름표는 쓰지 않는다. 아래로 옮긴다.

| 예전 | 지금 |
| --- | --- |
| `report`(업무 보고) | `data-preset="report" data-variant="status"` |
| `proposal`(제안) | `data-preset="report" data-variant="proposal"`. 제품 소개 제안이면 preview Demo 스토리라인 |
| `strategy`(전략) | 방향을 제안하면 report `proposal`, 선택지 중 하나를 고르면 compare `decision` |
| `tech`(기술 발표) | `data-preset="flow"`(구조 변경의 전/후 수치가 주인공이면 report `results`) |

## 덱 구성 (5~12장, 표지·제목 목차 포함)

1. **표지 = 결론**(`cover`). h1은 덱 전체의 결론 문장이다. 프리셋 대표 도식을 side·bottom·center·contrast·map 중 알맞은 위치에 둔다. 요약은 도식·리드에 흡수하고 결정할 것만 0~1행으로 남긴다.
2. **제목 목차**(`toc`). 모든 슬라이드 제목을 순서대로 작은 점 불렛으로 나열한 `ul`이고 항목은 그 슬라이드로 가는 링크다. 목차에는 번호와 쪽수를 표시하지 않는다.
   이 목록만 읽고 논리가 이어지지 않으면 슬라이드보다 제목부터 고친다.
3. **본 슬라이드.** 한 장 = 주장 하나 = 근거 하나 = 해석 한 줄. 프리셋 스토리라인 순서를 따른다.
4. **핵심 수치**(`stat`, 선택). 결론 숫자가 있으면 숫자 하나를 크게. page의 히어로 자리를 이 장이 대신한다.
5. **마지막 장**(`decision`). 결정·요청 한 문장을 세로 중앙에 크게 둔다. 구분선 아래 작은 `dl` 메타 2~3칸에 이미 나온 담당·기한·다음을 적는다.

## 슬라이드 종류 (`data-kind`)

| `data-kind` | 무엇 | 그림 | 대응 블록 |
| --- | --- | --- | --- |
| (생략) 근거 | 결론 제목 + 그림 + 요점 2~3개 나란히(split) | 필수 | [diagram](../blocks/diagram.md) |
| `cover` | 결론 h1 + 대표 도식 + 요약 0~1행 | 대표 도식 | [header](../blocks/header.md) 요약 행 |
| `toc` | 제목 목차(`nav.d0-slide`) | 예외 | — |
| `assertion` | 주장 한 문장만 | 예외 | Impact 기본 |
| `evidence` | 결론 제목 + 차트 + 해석 한 줄 | 차트 | diagram 막대·비율, [kpi-cards](../blocks/kpi-cards.md) 막대 변형 |
| `screenshot` | 실제 화면 + dim + spotlight + 짧은 주석 | 화면 | [mockup-frame](../blocks/mockup-frame.md)의 `figure.d0-shot` |
| `breakdown` | 전체 → 구성 요소 | 도식 | diagram 연결 그래프·와이어프레임 |
| `stat` | 숫자 하나 + 라벨 + 뜻 한 줄 | 큰 숫자가 그림 | [hero](../blocks/hero.md)의 수치 해부 |
| `summary` | 참고용 정리 목록 3행 이내 | 예외 | [checklist](../blocks/checklist.md) |
| `decision` | 큰 결정·요청 한 문장 + 구분선 + 작은 `dl` 메타 행 | 예외 | [slide-deck](../blocks/slide-deck.md) 마지막 장 |

그림 예외는 `toc`·`summary`·`decision`·`assertion`뿐이다. 커버에는 대표 도식을 둔다.

### 새 종류 넷

- **assertion.** 앞뒤 근거를 잇는 주장 한 문장만 크게 둔다. 그림·불릿·카드가 없고 기본이 Impact 면이다. 덱의 전환점(문제 제기, 추천, 결론)에 쓴다.
- **evidence.** 제목이 결론 문장이고, 그 결론을 증명하는 차트 하나와 "그래서 무엇을 뜻하나" 한 줄이 붙는다. 강조할 계열 하나만 blue다. 표보다 그래프가 나은 정보는 여기서 그래프로 그린다.
- **screenshot.** 실제 화면(목업 또는 이미지)을 크게 두고, 봐야 할 곳만 spotlight로 남긴 뒤 나머지를 흐린 막으로 덮는다. 주석은 번호를 맞춘 짧은 한 줄이다. 마크업은 mockup-frame의 `.d0-shot`(`.d0-shot__spot`, `.d0-shot__note`)이다.
- **breakdown.** 전체 모양을 먼저 그리고 그것을 이루는 부품 2~5개로 나눈다. 부품마다 이름 한 마디, 지금 이야기하는 부품만 blue다.

### 흔한 장면과 기존 블록

| 장면 | 쓰는 것 |
| --- | --- |
| Big Number | `stat` 슬라이드(hero 수치 해부), 전/후가 있으면 전 값 작게 |
| Options · Trade-off · Decision | compare의 [side-by-side](../blocks/side-by-side.md)(같은 축 열, 와이어 카드 `.d0-option__wire`) |
| Flow | [step-columns](../blocks/step-columns.md) 그림 변형(`data-variant="figure"`) 또는 diagram 단계 도식 |
| Timeline | [timeline](../blocks/timeline.md) SVG 시간 막대(`data-variant="timebar"`) |
| Architecture | `breakdown` 슬라이드, diagram 연결 그래프·와이어프레임 |

## 강조·색·면적

- **강조 순서.** 크기 → 위치 → 여백 → 무게 → 색. 색은 마지막 수단이다. 세부는 [composition](../composition.md).
- **Impact**(`data-emphasis="impact"`). 슬라이드 전체 면을 `var(--d0-blue-light)`로 채우고 글자는 grey-900, 강조 숫자는 blue-dark다.
  안에는 문장 하나, 숫자 하나, 그림 하나 중 하나만 둔다. 카드 금지. 어두운 배경은 쓰지 않는다.
  Impact 장면은 (a) 제목 60px 이상(1280 기준) 또는 (b) 72px 이상 큰 숫자 하나가 장면의 주인공일 때 성립한다. `stat` Impact는 숫자가 주인공이므로 제목은 일반 크기(약 39px)여도 된다. 둘 다 아니면 blue-light 면이어도 Impact로 세지 않는다.
  덱의 Impact 슬라이드는 전체의 20~30%다(8장이면 2장, 12장이면 3장). `quiet`는 받쳐 주는 장에 쓴다.
- **색 면적은 lint Warning.** 첫 화면 진한 포인트 채움 <1%는 "강조가 너무 약한지 확인", 1~15%는 정상, >15%는 "포인트 색이 배경처럼 쓰이는지 확인"이다. 게이트를 맞추려고 색 면적을 늘리지 않는다. 옅은 면은 경고 비율에서 빼며 Impact 장수는 따로 판정한다. 대비·WCAG 2.2 AA·의미색 글자 금지는 Hard로 유지한다. 정본은 [shell.md](../blocks/shell.md) 색 절이다.
- **그림 면적.** 커버는 대표 도식이 의미 있는 면적을 쓰는지 확인한다. 근거·evidence·breakdown·screenshot 장의 그림 영역은 슬라이드 면적의 60~80%를 차지한다. 기본 배치는 그림 + 요점 split이고,
  그림만 전체 폭이면 무대 좌우가 비지 않을 때(가로로 긴 도식)만 쓴다.
- **구도.** 같은 구도를 연속으로 두지 않고 밀도를 저 → 중 → 고 → 저로 엇갈린다([composition](../composition.md)).

## 대표 도식

슬라이드마다 그 주장의 근거 하나다. 전/후는 막대 두 개, 구조는 연결 그래프, 순서는 단계 도식, 화면은 `screenshot` 또는 와이어프레임이다.

- 데이터는 근거다. 차트 위에 결론 문장이 있고 강조할 계열 하나만 blue, 나머지는 grey다.
- 축 눈금·범례·격자선은 읽는 데 필요한 것만 남긴다. 값 라벨을 막대 끝에 달면 범례와 눈금을 지운다.
- 선 거의 없이 숫자·문구·객체 하나를 크게 보이는 장면은 diagram editorial 장르(`data-genre="editorial"`)를 쓴다.

## 문장 규칙

- **결론 제목.** 제목은 주제명이 아니라 결론 문장이다. 서술어(`-다`, `-요`, `-했다`, `-한다`)로 끝난다.
  `시장 규모` ✕ → `혼자 쓰는 팀이 이미 절반을 넘었다` ○. `현황`, `개요`, `분석 결과`, `Q&A` 같은 명사 제목은 실패다.
- 제목은 한두 줄(약 40자 이내)이다. 넘으면 보조 한 줄로 나눈다. 보조 한 줄은 제목을 되풀이하지 않고 범위·조건을 더한다(`지난 8주, 팀 A 기준`).
- 본문은 슬라이드당 3줄, 불릿 3개까지다. 남는 말은 발표자가 말로 한다.
- 숫자에는 해석을 붙인다. 해석 줄은 "그래서 무엇을 뜻하나" 한 문장, 출처 줄은 `출처: 내부 집계(합성)`처럼 짧게.
- 용어는 처음 나오는 슬라이드에서 괄호 속 짧은 비유로 푼다.

## page 원칙 중 덱에서 바뀌는 것

원칙 4번 섹션 상한(2~4개)·앞쪽 핵심 섹션 그림, 원칙 2·3번 첫 화면 규칙, 원칙 9번 히어로·h1 32/h2 20 고정 타이포·섹션 사이 64px,
줄 길이 50자, 720px 프레임, 도식 라벨 데스크톱 16px 상한 대신 이 파일의 구성과 Slide Gate, [slide-deck](../blocks/slide-deck.md)의 덱 규칙·덱 게이트를 따른다.
결론 수치는 히어로 대신 `stat` 슬라이드에 둔다. 나머지(글은 적게, 한 사실은 한 번(제목 목차 반복은 빼고 센다), 시맨틱, 토큰, 색, 접근성)는 그대로다.

## Slide Gate (의미 검사 우선)

마크업·크기 검사보다 먼저 본다. 하나라도 걸리면 마크업을 다듬기 전에 덱 구성을 고친다.

- [ ] 한 장에 주장이 하나다
- [ ] 제목이 주제명이 아니라 결론이다
- [ ] 제목만 이어 읽어도 논리가 이어진다(제목 목차를 소리 내어 읽어 본다)
- [ ] 모든 슬라이드가 앞 장 때문에 존재한다(빼도 이야기가 안 끊기는 장은 뺀다)
- [ ] 텍스트를 가려도 그림만으로 구조가 보인다
- [ ] 숫자마다 해석이 붙어 있다
- [ ] 표보다 그래프가 나은 정보(추세, 크기 비교, 비율)를 표로 두지 않았다
- [ ] 정보 없는 장식 도형·아이콘이 없다
- [ ] 화면 캡처에는 봐야 할 위치가 표시되어 있다(`screenshot`의 spotlight·번호 주석)
- [ ] 커버 도식이 주제의 실체를 보이고 프리셋마다 알맞은 위치·비율로 배치되며 요약은 0~1행이다
- [ ] 마지막 장은 `decision` 전용 구도이고 큰 요청·결정 한 문장 + 구분선 + 작은 `dl` 메타 2~3칸이다. 같은 무게의 불릿 목록이나 Impact를 두지 않고 메타는 덱에 나온 사실만 쓴다
- [ ] Impact 슬라이드가 전체의 20~30%이고, 각 Impact 면 안에 문장·숫자·그림 중 하나만 있으며, 제목 60px 이상 또는 72px 이상 큰 숫자 하나가 주인공이다(`stat`은 제목 일반 크기 허용)
- [ ] 장수가 표지·목차 포함 5~12장이다

마크업·타이포·키보드·인쇄 게이트는 [slide-deck](../blocks/slide-deck.md) 덱 게이트로 판정한다.

## 안티패턴

- 명사 제목만 있는 덱(`배경`, `현황`, `결론`). 제목 목차를 읽어도 이야기가 안 된다.
- 한 슬라이드에 문제·기능·장점·화면·성과·일정을 전부 넣기.
- 문서를 붙인 덱: 여러 줄 문단, 불릿 4개 이상, 표 전체 붙여 넣기.
- 의미 없는 아이콘·도형·그라디언트·3D·사람 일러스트, 모든 계열을 다른 색으로 칠한 차트.
- 그래프만 있고 결론 문장이 없음, 결론과 그래프가 다른 말을 함.
- 좁은 그림 하나만 전체 폭 무대에 올려 좌우가 빈 근거 슬라이드.
- 표지가 제목·날짜뿐이라 첫 장만 보고는 결정할 것을 모름.
