# ELI5 Design

처음 보는 사람도 그림으로 구조를 먼저 이해하고, 짧은 글로 이유와 맥락까지 이해하는 HTML 설명 문서를
Day0 시각 언어로 만드는 에이전트 스킬입니다. 시안 비교, 절차 설명, 보고서, 설치 가이드, 장애 회고처럼
누군가에게 무언가를 쉽게 보여 줘야 하는 문서에 씁니다. 기본은 혼자 읽어도 이해되는 한 장짜리 페이지이고,
같은 내용을 발표나 화면 공유용으로 한 장씩 넘기는 덱으로도 만들 수 있습니다.

## 사용 조건

- 시안이나 옵션을 나란히 놓고 결정을 받아야 할 때
- 절차, 구조, 결과물의 모양을 처음 보는 사람에게 설명할 때
- 보고서, 가이드, 일정, 사건 경위, 용어 정리를 한 문서로 보여 줄 때
- 위 내용을 발표나 화면 공유로 한 장씩 넘기며 설득하는 덱으로 보여 줘야 할 때
- `/eli5-design` 으로 명시 호출할 때

설명 페이지가 아닌 Day0 제품 화면은 `day0-design`, 문구만 다듬는 작업은 `ux-writing`을 사용합니다.
설명 목적이 없는 일반 화면과 랜딩 디자인에는 쓰지 않습니다.

## 핵심 동작

### 출발 원칙

"아무것도 모르는 사람에게, 큰 그림과 적은 글로 된 HTML로 설명하라"는 원칙을 글을 적게 쓰라는 뜻이 아니라
같은 말을 그림과 글로 두 번 하지 말라는 뜻으로 읽습니다. 그림이 구조를 설명하고, 짧은 글이 이유·근거·조건을 보완합니다.
같은 숫자와 결정은 한 곳에만 쓰지만, 중복을 지운다고 이해에 필요한 맥락까지 지우지는 않습니다.

### 독자 질문으로 섹션을 나눕니다

먼저 독자가 다 읽고 나서 할 수 있어야 하는 것을 정하고, 거기에 필요한 질문을 한 줄씩 적습니다.
섹션 하나는 질문 하나에 답합니다. 섹션 수에 목표나 하한은 없고, 핵심 질문에 답하지 못하면 실패로 봅니다.
7개를 넘으면 묶을 수 있는 질문이 있는지 다시 봅니다. 완성도는 글자 수가 아니라 Page Depth Gate로 확인합니다.
핵심 질문에 모두 답했는지, 결론에 근거가 있는지, 변화에 원인이나 영향이 있는지, 결과를 바꾸는 조건이 적혔는지,
다음 행동이 분명한지, 짧게 만들려고 맥락을 지우지 않았는지를 봅니다.

### 용어 계층

| 층 | 뜻 |
| --- | --- |
| Principle | 변하지 않는 원칙(그림 먼저, 첫 화면 SVG 도식, 한 사실은 한 번, Day0 토큰, 접근성) |
| Pattern | 정보를 설명하는 방식: 비교(compare), 절차(flow), 미리보기(preview), 보고(report), 가이드(guide), 일정(timeline), 사건(incident), FAQ(faq) |
| Block | 공용 부품: explanation, evidence, before-after, checkpoint, status rail, question-answer, closing과 그림·목록 블록 |
| Layout | 배치, 곧 구도 |
| Recipe | 목적별 Pattern과 Block 조합(선택) |
| Output | 한 장짜리 페이지(page) 또는 한 장씩 넘기는 덱(deck) |

Pattern은 어떻게 설명할지, Block은 무엇으로 표현할지, Layout은 어디에 놓을지, Recipe는 무엇을 함께 쓰면 좋은지를 정합니다.
이 계층은 개념 구분이고 작업 순서가 아닙니다. 실제로는 독자가 알아야 할 것을 정한 뒤, 맞는 레시피가 있으면 출발점으로 삼고,
필요한 패턴과 블록을 고르고, 구도를 잡고, 출력 형식에 맞게 조정합니다.

### 패턴은 섹션마다 섞습니다

한 페이지 전체를 지배하는 주 패턴은 없습니다. 장애 회고라면 사건 섹션 옆에 타임라인과 비교 섹션을 섞습니다.
섹션에는 `data-pattern` 이름표를 달고, 첫 화면 도식은 첫 섹션 패턴의 대표 도식으로 그립니다. 패턴 문서는 그 질문에 답하는
추천 블록과 구도, 페이지 대부분을 차지할 때의 자연스러운 깊이, 함께 자주 섞는 패턴, 덱으로 낼 때의 순서를 담습니다.
블록은 패턴이 소유하지 않으므로 어느 패턴에서나 모든 공용 블록을 빌려 쓸 수 있습니다.

### 공용 정보 블록

| 블록 | 답하는 것 |
| --- | --- |
| explanation | 그림이 보여 줄 수 없는 배경·이유·뜻·영향·조건·예외. 라벨 하나에 1~3문장이고, 그림 옆이 비면 그 열에 둡니다 |
| evidence | 주장 한 줄과 근거(숫자·출처·전/후·예시)의 짝 |
| before-after | 같은 대상의 전과 후(문제→수정, 기존→개선, 예상→실제) |
| checkpoint | 여기까지 하면 무엇이 완성되는지 |
| status rail | 지금 어디에 있는지(완료·진행·예정) |
| question-answer | 독자가 실제로 가질 만한 질문과 답 |
| closing | 문서가 남길 일 하나(결정·요청·행동·기준·지킬 것)와 담당·기한 메타 |

기존 공용 블록으로 표현할 수 있으면 새 블록을 만들지 않습니다. 새 모양은 변형으로, 새 배치는 구도로, 새 조합은 레시피로
더하고, 둘 이상 패턴에서 반복되는 새 의미 구조만 새 공용 블록이 됩니다. 긴 따라하기는 작업 목적이 바뀌는 지점에서 구간으로 나누고,
현재 구간만 펼친 채 status rail로 전체 위치를, 구간 끝 checkpoint로 결과를 보여 줍니다.

### 레시피는 선택입니다

장애 회고, 기능 출시 보고, 설치 가이드, 기능 소개, 의사결정 문서, 상태 보고 여섯 가지 레시피가 질문 순서와 패턴, 추천 블록을
미리 짝지어 둡니다. 출발점일 뿐이라 독자 질문에 없는 섹션은 빼고 필요한 질문은 더합니다.

### page와 deck

page는 혼자 읽어도 이해되는 시각 문서로 구조, 맥락, 근거, 조건, 해석을 함께 담습니다. deck은 발표자와 함께 보는 자료로
한 장에 주장 하나와 최소한의 글만 둡니다. 혼자 읽히는 게 주목적이면 page를 쓰고, 발표자 없이 전달될 덱이면 필요한 맥락과 출처를 덱 안에 남깁니다. 둘은 같은 패턴과 블록을 쓰고 밀도 규칙만 다릅니다. 덱은 주 패턴 하나의 스토리라인을 따르고
표지·목차 포함 5~12장이며, 결론 문장 제목, 그림 면적, 전체의 20~30%인 강조 장면, closing 마지막 장 규칙을 지킵니다.

### 시각 규칙

첫 화면에는 주제의 실제 모양을 그린 인라인 SVG 도식을 두고, 첫 화면 안에서는 그림 면적이 글 면적보다 커야 합니다.
텍스트 상자를 화살표로 이은 그림은 도식으로 인정하지 않습니다. 첫 화면 아래 섹션은 핵심 구조가 있을 때 그림을 권장하고,
그림 없는 섹션은 질문→답, 라벨→설명, 주장→근거처럼 구조를 가진 블록으로 짓습니다. 그림은 키워서 폭을 채우지 않고
(글자 없는 도식도 360px(wide 400px) 상한, 가로로 긴 타임라인·단계 줄만 720px) 옆 설명이나 2열 배치로 채웁니다.
본문 한 줄은 공백 포함 50자 이하이고, 문단을 좁히는 대신 글 블록 컨테이너를 32em으로 둡니다.

타이포는 제목 32px, 섹션 20px, 본문 15px이고 섹션 사이는 64px입니다. 강조는 크기, 위치, 여백, 무게, 색 순서로 겁니다.
첫 화면 진한 포인트 색 면적은 lint 경고로만 확인합니다. 1% 미만은 "강조가 너무 약한지 확인", 1~15%는 정상,
15% 초과는 "포인트 색이 배경처럼 쓰이는지 확인"이고 게이트를 맞추려고 색 면적을 늘리지 않습니다. 대비와 WCAG 2.2 AA,
의미색 글자 금지는 반드시 지킵니다. 타이포와 여백 값은 `day0-design`보다 우선하고, 색·radius·모션·컴포넌트 규칙은 `day0-design`을 따릅니다.

결과는 단일 HTML 파일이고 라이트 전용으로 배경을 명시합니다. 설명 문단은 부모 폭을 그대로 쓰고 `text-wrap: balance`는 제목에만 둡니다.
한 artifact 안에서 여러 페이지를 탭으로 보여 줄 때는 페이지 HTML을 내장해 `srcdoc`으로 띄웁니다. 호스트에 artifact 발행 기능이 있으면 발행합니다.

## 사용 예

```text
/eli5-design 알림 주기를 매일로 할지 매주로 할지 결정 페이지 만들어줘.
```

```text
지난주 내보내기 장애 회고를 쉽게 설명하는 페이지 만들어줘. 고른 대응과 버린 대응도 비교해서.
```

```text
팀 A 신규 입사자용 설치 가이드를 설명 페이지로. 단계가 열두 개쯤 돼.
```

```text
알림 개편 3분기 진행 상황을 쉽게 보는 발표 슬라이드로 만들어줘.
```

## 요구 사항

`day0-design` 스킬을 함께 설치하는 것을 권장합니다. 이 스킬은 토큰 값을 갖지 않고
`day0-design`의 `tokens.css` 파일 전체를 HTML `<style>`에 그대로 인라인합니다.
`day0-design`을 어디서 찾는지는 `SKILL.md`의 탐색 순서를 따릅니다. 로컬에 없으면 공개
저장소 원본을 읽으므로 네트워크가 필요하고, 그마저 실패하면 토큰을 추측하지 않고 멈춥니다.
결과물 HTML을 넘길 때는 파일이든 artifact 발행이든 `scripts/subset_font.py`로 페이지에 쓴 글자만 담은
서브셋 폰트를 인라인해 외부 요청을 없앱니다. 도구를 쓸 수 없을 때만 Pretendard Variable 웹폰트 링크 하나를 남기고 그 사실을 알립니다.
