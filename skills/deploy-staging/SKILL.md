# 스테이징 배포

현재 저장소가 정의한 배포 경로를 따라 스테이징에 반영하고, 배포된 revision과 실행 결과를 확인한다. 브랜치 이름, 워크플로 파일, 빌드 명령, PR 필요 여부를 미리 가정하지 않는다.

## 배포 경로 확인

작업을 바꾸기 전에 다음 근거를 확인한다.

- 저장소의 `AGENTS.md`, `README`, 기여 지침과 배포 문서
- 현재 브랜치, upstream, remote, status와 `git worktree list`
- CI 워크플로, 배포 설정, 패키지 스크립트
- 조회할 수 있다면 원격 기본 브랜치, 보호 규칙, 필수 검사와 최근 스테이징 실행

설정 파일을 새로 만들거나 정리해야 할 때는 [설정 reference](references/deployment-config.md)를 읽는다. 배포 경로는 저장소 정책, 실제 CI 트리거와 원격 보호 규칙을 모두 충족해야 한다. 이 근거들이 충돌해 허용 경로를 확정할 수 없으면 실행 전에 사용자에게 필요한 선택만 묻는다. 조회 권한이 없어 원격 규칙을 확인할 수 없다면 확인된 로컬 근거와 불확실성을 알리고, 추측으로 보호 규칙을 우회하지 않는다.

Git 상태를 반복해서 수집할 때는 `python3 scripts/preflight.py --repo <repository> --remote <remote> --target-branch <branch>`를 실행한다. 확인한 remote 이름을 반드시 전달한다. 이 도구는 현재 브랜치와 SHA, 변경 개수, 설정된 remote 이름, 대상 브랜치 SHA와 worktree 점유를 읽기 전용 JSON으로 반환한다. fetch하거나 정책을 판정하지 않으며 `remote_tracking_sha`는 마지막 fetch 시점의 로컬 추적 ref일 뿐 원격의 최신 상태를 증명하지 않는다. 출력은 다른 근거와 함께 해석한다.

저장소가 허용하는 경로를 다음 중 하나로 확정한다.

- 작업 브랜치 push가 배포를 시작하는 방식
- 통합 브랜치로 PR을 병합한 뒤 배포하는 방식
- 승인된 브랜치에 fast-forward 또는 merge push하는 방식
- 수동 workflow dispatch나 배포 도구를 실행하는 방식

필요한 대상 브랜치, 환경, 워크플로 입력, 사전 검사와 성공 판정 수단도 함께 특정한다. 설정이 부족하면 확인 가능한 부분을 먼저 끝내고, 결과를 바꾸는 누락값만 질문한다.

## 실행 권한

스테이징 배포 요청은 확인된 배포 경로에 필요한 커밋, push, PR 생성·병합 또는 워크플로 실행을 승인한 것으로 본다. 사용자가 이미 배포나 push를 명시적으로 요청했다면 같은 동작을 다시 승인받지 않는다. 다만 커밋 작성 요청만으로 push나 배포 권한을 넓히지 않는다.

스테이징 배포 결과 확인만 요청한 경우에는 읽기 전용 조회만 수행한다. 커밋, push, PR 생성·병합, 워크플로 재실행이나 새 배포를 하지 않는다.

배포 전에 대상, 변경 내용, 실행할 배포 경로를 구체화한다. 확인된 정책이 별도 승인을 요구하거나, 요청 범위를 넘어서는 선택이 남아 있을 때만 사용자에게 묻는다.

## 변경과 커밋

배포 대상 diff와 untracked 파일을 확인한다. 다른 사용자나 세션의 변경을 stage, 수정, 되돌리거나 배포에 섞지 않는다. 소유권을 구분할 수 없으면 관련 경로를 보고하고 멈춘다.

커밋이 필요하고 승인 범위에 포함되면 변경 의도에 맞는 경로만 명시적으로 stage한다. `git add -A`처럼 범위가 넓은 명령은 피한다. 커밋 메시지나 분할 판단이 필요한 경우 설치되어 있다면 `conventional-commits` 스킬을 적용하고, 그 규칙을 여기서 중복 정의하지 않는다.

배포 경로가 깨끗한 작업 트리를 요구하면 관련 변경을 먼저 커밋한다. 사용자의 변경을 임의 stash하지 않는다.

## 안전한 배포

필요한 검사만 실행하고 결과를 확인한다. CI가 같은 검사를 신뢰성 있게 수행한다면 불필요하게 반복하지 않는다.

브랜치를 바꿔야 할 때는 다른 worktree의 점유 상태와 현재 worktree의 변경을 확인한다. 통합 브랜치가 다른 worktree에 있으면 그 위치와 상태를 확인해 안전할 때만 그 worktree에서 수행한다. 다른 작업이 있거나 소유권이 불명확하면 건드리지 않는다. 현재 worktree에서 브랜치를 바꿨다면 성공·실패와 관계없이 원래 브랜치로 복귀하되, 복귀가 변경을 덮어쓸 수 있으면 멈추고 현재 상태를 보고한다.

push가 non-fast-forward로 거부되거나 병합 충돌이 나면 중단한다. `--force`, `--force-with-lease`, 보호 규칙 우회, 필수 검사 생략, 타인의 브랜치 변경을 사용하지 않는다. 충돌을 자동 해결하거나 대상 브랜치를 작업 브랜치로 역병합하지 말고, 실패 지점과 안전한 다음 선택을 제시한다.

PR 방식이면 저장소 템플릿과 필수 검사를 따른다. 병합 권한이나 필수 승인이 없으면 준비된 PR과 남은 조건을 보고한다. 수동 워크플로라면 확정한 ref와 입력을 사용하고, 실행 ID를 기록한다.

## 성공 확인

push, PR 병합, workflow 시작만으로 배포 성공을 단정하지 않는다. 다음을 연결해서 확인한다.

1. 배포 대상으로 확정한 commit SHA
2. 해당 SHA를 사용한 CI run 또는 배포 기록
3. 대상 환경의 최종 성공 상태

가능하면 실행 URL, 배포 URL, 환경 이름과 완료 시각도 확인한다. 배포 시스템이 merge commit이나 빌드 산출물 revision을 사용하면 작업 commit과 실제 배포 revision의 관계를 기록한다.

실행이 진행 중이면 기본적으로 완료 또는 실패까지 합리적인 간격으로 확인한다. 사용자가 시작만 요청했거나 명시한 시간 한도에 도달했거나 도구·권한 문제로 더 조회할 수 없을 때만 진행 중 상태와 재조회 방법을 보고한다. 결과를 조회할 수 없으면 "요청됨" 또는 "확인 불가"로 표현하고 성공으로 보고하지 않는다.

최종 보고에는 배포 경로, 포함한 commit, 원격에 반영된 정확한 revision, run/deployment 상태와 링크, 실행한 검사, 현재 브랜치, 실패나 미확인 항목을 포함한다.
