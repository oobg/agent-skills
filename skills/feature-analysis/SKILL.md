# Feature Analysis

구현물에서 실제 제품의 기능 구조를 복원한다. 최종적으로 이 화면이 어떤 업무를 지원하고, 사용자가 무엇을 할 수 있고, 어떤 상태와 규칙이 존재하며, 무엇이 구현되고 무엇이 의도만 있는지에 답한다.

복원하는 관계는 `Surface → Action → Handler → Rule → Mutation → State Transition → Side Effect → Feedback`이고, 이를 다시 `Feature → Workflow → Product Capability`로 묶는다.

## 역할 경계

- 코드 품질, 버그, 네이밍, 패턴은 판정하지 않는다. 기술 구조는 상태가 어디에 살고 데이터가 어디서 오며 persistence가 있는지처럼 제품 의미를 설명하는 데 필요한 만큼만 읽는다.
- 시각적 완성도, 디자인 취향, AI 슬롭 여부는 판정하지 않는다. 디자인 분석은 화면별 입력, 처리, 출력, 예외와 인터랙션 활성 조건을 읽는 화면 설계 분석과, 요청이 있을 때 토큰·위계·컴포넌트 상태·모션을 재현 가능한 수준으로 적는 디자인 명세를 뜻한다.
- 코드를 수정하지 않고, 코드에 없는 DB 스키마나 API를 만들어 넣지 않는다. 제안은 (제안) 표기를 붙여 관찰과 구분한다.

## 입력 게이트

분석 전에 대상을 분류하고 기준을 기록한다. 세부는 `references/inventory.md`를 따른다.

- 입력 형태: 원본 코드, 빌드 결과물, 배포된 서비스, 정적 스냅샷(스크린샷·영상). 형태마다 분석 경로가 다르고 UNKNOWN으로 고정되는 항목이 다르다. 빌드 결과물은 업무 규칙 대부분이, 배포된 서비스는 소스맵 없는 코드 전부가, 스냅샷은 handler 이하 전부가 UNKNOWN이다.
- 기준을 적는다. 커밋 해시, 파일 해시, URL 중 확인 가능한 것과 분석 시점을 리포트 개요에 남긴다.
- 시드 데이터, mock 배열, 영속성 없음, 자리 표시자 주석 중 하나라도 있으면 프로토타입이다. 프로토타입에서는 데이터 값, 스텁의 정확도, id 충돌·성능·보안·동시성, 선언되지 않은 뷰포트와 테마를 판정하지 않는다. 판정하는 것은 체인 완결성, 상태 전이와 정의의 일관성, 규칙의 적용 범위, destructive 보호, 의도와 구현의 어긋남이다. 세부는 `references/inventory.md`의 프로토타입 판정 규칙을 따른다.

## 작업 방식

- 원본을 변경하지 않는 read-only 분석이 기본이다. 스크립트 산출물과 중간 파일은 원본 밖에 쓴다.
- 반복 실행 시 같은 결과가 필요한 탐색과 수집은 스크립트로 한다. 파일, 라우트, 이벤트, 상태, API 호출, 스타일 토큰, 부작용, 스텁 마커처럼 기계적으로 수집 가능한 항목을 매번 수작업으로 찾지 않는다. 기본 수집기는 `scripts/collect_inventory.py`이고, 대상에 맞는 패턴이 필요하면 스크립트를 확장하되 원본은 건드리지 않는다.
- 기계적 수집 결과는 같은 입력과 같은 수집기 버전에 대해 결정적이어야 한다. 실행 시각 같은 run metadata는 수집 결과와 분리하고, 이전 분석과 diff할 때 제외한다.
- 자동 추출 결과는 Inventory다. 최종 기능 판단은 원본 코드 또는 런타임 증거와 대조한 뒤에만 내린다. 수집기가 잡은 항목을 그대로 Feature로 쓰지 않고, 수집기의 0건을 부재의 증거로 쓰지 않는다. 0건은 현재 패턴이 검출하지 못했다는 뜻이다.
- 분석 도구나 스크립트의 실패는 제품 결함이 아니다. 도구 실패는 커버리지 절에 적고 결함 목록에 넣지 않는다.

## 원칙

1. 제품 의미를 코드 구조보다 우선한다. 업무 워크플로우, 사용자 액션, 상태 전이, 업무 규칙, 데이터 변경, 자동화 순으로 설명하고, 상위 의미가 설명되면 하위 구현 세부를 나열하지 않는다.
2. 화면에 있다고 기능으로 확정하지 않는다. `UI → Event → Handler → Validation → Mutation → Render/Side Effect` 체인을 끝까지 추적하고, 끊긴 지점을 기록한다.
3. 흩어진 증거를 하나의 Feature로 합친다. render 함수의 버튼, listener의 click 처리, utility의 validation, state 객체의 값, 다른 함수의 이력 생성은 별개 기능이 아니다.

## 증거 규율

- 파일과 위치를 짚지 못하면 사실로 세지 않는다. 표의 Evidence 열은 `파일:줄` 또는 `파일#함수명` 형식이고, 런타임 증거는 `runtime:` 접두어로 구분한다.
- 정적 분석과 런타임 검증을 구분한다. 실행해야 확인 가능한 동작(비동기 순서, 타이밍, hover·focus, 렌더 결과, 외부 응답 처리)은 코드만으로 CONFIRMED하지 않는다. 정적 증거만 있으면 PARTIAL이다.
- 도달 경로가 없는 것을 봤다고 적지 않는다. 정의만 있고 호출되지 않는 함수, 어떤 화면에서도 열리지 않는 모달은 L1 이하다.
- 코드와 주석, 명칭, 첨부 문서가 어긋나면 코드가 이긴다. 어긋남 자체는 기록한다.
- 구현되지 않았다고 판단할 때는 탐색한 범위를 먼저 적는다. 어떤 파일과 패턴을 찾았는지 적고, 찾지 않은 곳을 없다고 쓰지 않는다.
- 결과에 커버리지를 선언한다. 읽은 파일과 화면, 건너뛴 것, 그 이유를 적는다. 조사 결과는 본 것만 말하므로 못 본 범위는 따로 써야 드러난다.
- Confidence는 CONFIRMED, PARTIAL, INFERRED, UNKNOWN 네 가지다. UNKNOWN을 일반 관행으로 채우지 않고 INFERRED를 CONFIRMED처럼 쓰지 않는다.

## 분석 순서

`references/analysis-graph.md`의 노드 순서를 따른다.

```text
Inventory → Interaction · Domain · State · Business Rule → Feature → Workflow → Verification → Output
```

- 각 노드는 이전 노드의 결과를 입력으로 쓴다. Inventory 결과를 바로 명세로 바꾸지 않는다.
- 상태 축은 업무 상태, UI 상태(기본, 로딩, 빈 상태, 오류, 성공), 파생 상태로 분리한다.
- 대상이 크면 노드별 중간 산출물을 파일로 남기고 다음 노드가 그 파일을 읽는다. 요약을 거치며 이유와 제약이 먼저 사라지므로 중간 산출물에는 Evidence를 유지한다.

## 등급

Priority, Level, Confidence, 누락 등급 네 축을 `references/rubric.md`대로 매긴다. 축 사이 연결 규칙이 핵심이다.

- Mutation이 CONFIRMED가 아니면 L3 이상을 주지 않는다. mock 배열 변경은 persistence가 아니다.
- Confidence가 INFERRED 이하인 Feature는 P0으로 확정하지 않는다.
- 누락은 여섯 조건 중 하나를 만족할 때만 기록하고 BLOCKING, IMPORTANT, OPTIONAL로 나눈다.

## 산출물

산출물은 두 층이다.

- 분석 리포트는 `references/report.md`의 요약 다섯 절을 기본으로 하고, 상세 분석은 부록으로 붙인다. 요약층에 Confidence가 섞여도 된다.
- 핸드오프 문서는 사용자가 개발 착수나 외주 전달용을 요청할 때만 `references/handoff.md`로 만든다. 핸드오프 본문에는 CONFIRMED만 들어가고, INFERRED와 UNKNOWN은 오픈 이슈 절로 뺀다. 확정되지 않은 값에는 (제안)을 붙인다.

- 디자인 명세는 사용자가 대상의 디자인을 레퍼런스나 초안으로 쓰겠다고 요청할 때만 `references/design-spec.md`로 만든다. 자사나 본인 산출물이면 토큰과 실측값을 그대로 남기는 실측 스냅샷 모드, 제3자 산출물이면 위계·리듬·상태 모델 같은 장르 문법만 남기고 색상 값·서체·로고·카피를 빼는 파생 규칙 모드다. 판독 기록은 재현 허가가 아니다. 스크린샷만으로는 만들지 않는다.

규모에 맞춘다. 화면 하나면 절을 줄이고 표를 합친다. 비어 있는 절은 채우지 않고 지운다.

## 평가

리포트 5절에서 P0과 P1 Feature의 장점, 단점, 바꾸면 좋을 것을 쓴다. 각 항목은 관찰된 사실 하나에 묶이고 근거 유형은 체인 완결성, 규칙 일관성, 워크플로우 단축, 보호 장치, 누락 조건 다섯 가지로 제한한다. 변경 제안에는 (제안)을 붙인다. 일반 관행이나 취향만으로 단점을 쓰지 않는다.

## 검증

P0과 P1 Feature는 명세로 옮기기 전에 원본 코드에 대해 다시 확인한다. Trigger 존재, Handler, Mutation, Business Rule, Side Effect, 다른 Feature와의 중복, Workflow 연결, 추론을 사실처럼 쓴 곳 여덟 가지를 본다. 하나라도 확인되지 않으면 Confidence를 낮춘다.

자기 검증만으로 끝내지 않는 경로를 열어 둔다. checker 에이전트를 쓸 수 있으면 `references/rubric.md`와 리포트를 넘겨 P0과 P1을 채점하게 하고, 주장과 코드가 다르면 코드를 따른다.

## 온톨로지 보강

같은 제품의 제품 정의서나 이전 분석이 있을 때만 `references/ontology-boost.md`를 열어 입력을 보강한다. 회수 결과는 입력 후보이고 판정 기준을 넓히지 않는다.

## 종료 기준

핸드오프를 받는 개발자가 다시 물을 질문이 남았는지가 잣대다. P0과 P1이 검증되고, 상태 축과 워크플로우가 연결되고, 누락과 격차가 등급과 함께 기록되고, 커버리지가 선언되면 끝낸다. 결론을 바꾸지 않는 관점을 더 발굴하지 않는다.
