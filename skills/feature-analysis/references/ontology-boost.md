# 선택 모듈: 온톨로지 입력 보강

같은 제품의 제품 정의서, 이전 분석, 데모와 실코드의 격차 기록이 온톨로지에 있을 때만 사용한다. 일반 분석의 필수 단계가 아니며, 상위 domain-ontology 스킬의 자동 조회 트리거를 제한하지 않는다.

## 조회 규율

domain-ontology 스킬에 조회를 위임하고 `~/.ontology/AGENTS.md`와 `~/.ontology/docs/recall.md`의 정본 절차를 따른다. 이 파일에서 SQL이나 별도 조회 규약을 지어내지 않는다.

- 분석 대상이 회사 제품이면 company와 허용된 shared 범위를 조회한다. 개인 프로젝트면 personal과 shared다.
- 대상 동일성이나 허용 범위를 확인할 수 없으면 조회하지 않고 제공된 코드만 사용한다.
- 다른 tenant로 범위를 자동 확장하지 않는다.

DB, 정본 문서 또는 domain-ontology 스킬에 접근할 수 없으면 코드만으로 계속하고 조회하지 못했음을 알린다. 정상 조회가 0건인 경우는 접근 실패와 구분해 선례가 없다고 처리한다.

## 사용 범위

회수한 내용은 다음에만 쓴다.

- 도입 배경과 의도 채우기. 코드에는 왜 만들었는지가 없으므로 선례가 있을 때만 리포트 2절의 도입 배경을 채우고 출처를 적는다.
- 명칭과 도메인 어휘 맞추기. 선례가 쓰는 모듈명과 상태명을 따라 ID와 표기를 정한다.
- 이전 분석과의 격차 비교. 그때 없음(로드맵)이었던 것이 지금 있는지 코드로 다시 확인한다.

회수 결과는 입력 후보다. 과거 기록이 결함이나 부재를 말해도 지금 코드에서 살아 있는지 확인한 뒤에만 리포트에 올린다. 화면은 배포마다 바뀌므로 과거 기록은 파일을 열어 보라는 신호이지 현재 상태의 증거가 아니다.

온톨로지는 판정 기준을 넓히지 않는다. 선례에 있다는 이유로 코드에서 확인되지 않은 기능을 CONFIRMED로 올리지 않는다.

## 적재 경계

분석 결과, 코드 발췌, 대화 로그를 자동 적재하지 않는다. 새 정보를 저장하려면 별도의 사용자 동의와 문서별 tenant 확인이 필요하며 실제 적재는 domain-ontology 절차를 따른다. 회사 코드 발췌나 분석 결과를 공개 저장소에 보관하지 않는다.
