# 핸드오프 문서 템플릿

개발 착수나 외주 전달용으로 사용자가 요청할 때만 만든다. 분석 리포트와 다른 규칙이 적용된다.

## 규칙

- 본문에는 CONFIRMED 항목만 넣는다. INFERRED와 UNKNOWN은 오픈 이슈 절로 뺀다. 추론이 요구사항 문장으로 굳으면 분쟁의 근거가 된다.
- 코드에 없는 값을 제안할 때는 열 이름이나 값에 (제안)을 붙인다. API 엔드포인트(제안), 컷오프(제안), 정책(제안)처럼 쓴다.
- 본문에는 파일 경로와 코드 조각을 넣지 않는다. 금방 낡는다. Evidence는 부록의 추적표에만 둔다.
- 디자인 표현("버튼을 크게")은 넣지 않는다. 클릭 시 동작만 적는다.
- 문서 머리에 기준 버전과 분석 일자를 적어 어느 구현물을 읽은 문서인지 남긴다.
- 현행 관측, 아직 정하지 않은 것, 운영 전환에 필요한 요구, 후속 범위 제안을 섞지 않는다. 현행 관측만 본문 명세에 두고 나머지는 각각 오픈 이슈, 운영 규격, 릴리스 구분으로 보낸다.
- 최종 작성 뒤 같은 Feature나 Rule이 기능 명세, 상태 전이, 업무 규칙, 운영 규격에 반복되면 허용 조건, 되돌림, 기준값, 단위를 교차 대조하고 축약하며 빠진 조건을 복원한다.

## 구조

### 0. 문서 정보

기준 버전, 분석 일자, 작성자, 대상 범위, 이 문서가 다루지 않는 것, 최종 사용자 수준과 그 출처·확정 여부. 최종 사용자는 요청자나 핸드오프 독자와 구분한다.

### 2. 기능 명세

| 기능 ID | 기능명 | 입력 | 처리 | 출력 / 예외 | 우선순위 |
| ------- | ------ | ---- | ---- | ----------- | -------- |

입력은 사용자 입력과 읽는 데이터, 처리는 validation과 규칙과 mutation, 출력은 화면 변화와 side effect, 예외는 실패 경로다.

### 3. 화면별 상태와 인터랙션

화면마다 다음을 적는다.

- 화면 목적 한 문장
- 상태 목록: 기본, 로딩, 빈 상태, 오류, 성공 후 후속 액션
- 인터랙션 활성 조건: 어떤 상태에서 어떤 버튼이 활성·비활성인가
- 데이터 필드 매핑: 화면 요소가 어느 entity의 어느 필드를 보이는가

### 6. 부록: 운영 규격

각 항목은 코드에서 확인된 것과 (제안)을 구분한다.

- A.1 권한 매트릭스: 기능 × 역할
- A.2 비즈니스 로직 임계치: 기능, 지표, 산식과 컷오프
- A.3 입력 유효성 규격: 필드, 검사 항목, 규격
- A.4 동시성과 상태 충돌: 화면, 충돌 시나리오, 정책
- A.5 외부 연동 예외: 상황, 처리, 영향 화면
- A.6 감사 이력: 변경 종류, 기록 여부, 기록 내용

### 7. 릴리스 구분

| 기능 ID | 현재 Level | 이번 범위 | 다음 버전 |
| ------- | ---------- | --------- | --------- |

무엇을 첫 릴리스에 넣고 무엇을 미루는지는 사용자 결정이다. 이 절은 결정을 위한 후보표이고 (제안)이다.

첫 릴리스의 핵심 업무 흐름에는 완료 기준(제안)을 적는다. 시작 조건, 성공으로 보는 상태·데이터 변경, 필수 side effect, 허용할 실패 경로를 포함하되 코드에서 확인된 현행 동작과 섞지 않는다. 미결정 규칙은 오픈 이슈 ID를 참조하고 결정 후 적용할 조건으로 적는다. 선택지를 임의로 완료 기준에 고정하지 않고, 특정 안을 제안하면 대안과 결정 필요 여부를 별도로 표시한다.

### 8. 오픈 이슈

| 이슈 | Confidence | 확인 방법 | 결정 시점(제안) | 영향 기능 |
| ---- | ---------- | --------- | ---------------- | --------- |

INFERRED와 UNKNOWN 전부가 여기 온다. 확인 방법에는 누구에게 무엇을 물어야 하는지 또는 어느 코드를 열어야 하는지를 적는다. 결정 시점에는 착수 전, 연동 전, 릴리스 전처럼 미결정 상태를 끝내야 할 경계를 (제안)으로 적는다.
