# Domain Ontology

대화마다 같은 배경을 다시 설명하지 않도록 회사, 개인, 공용 지식을 SQLite
온톨로지에 연결하는 에이전트 스킬입니다. 기존 지식이 답을 바꿀 수 있을 때는 먼저
조회하고, 오래 남길 자료는 사용자 동의를 받은 뒤 원문과 근거를 보존해 적재합니다.

## 언제 사용하나요?

- 이전 결정이나 축적된 맥락을 참고해 답해야 할 때
- 제품, 전략, 경쟁, 법률, 개인 우선순위에 관한 질문을 받을 때
- 보고서, 연구 결과, 전략 문서처럼 재사용할 자료가 들어왔을 때
- “온톨로지에서 찾아줘”, “이거 적재해줘”라고 요청할 때

코드 작업, 단순 편집, 일반 상식, 가벼운 대화, 현재 파일만으로 답할 수 있는
질문에는 조회를 강제하지 않습니다.

## 조회와 적재

### 조회

축적된 지식이 답을 실질적으로 바꿀 수 있으면 별도 확인 없이 읽기 전용으로
조회합니다. 개념, 토픽, claim 근거를 연결해 기존 결정과 충돌, 보강점, 빈틈을
찾은 뒤 실제 질문에 답합니다.

### 적재

온톨로지 쓰기는 항상 사용자 동의가 필요합니다. 적재할 자료의 범위와 테넌트를
확인한 뒤 다음 순서로 진행합니다.

```text
원문 보존 → 기존 개념 조회 → claim 추출 → 증분 적재 → 그래프 연결 확인
```

침묵은 동의로 간주하지 않습니다. 조회 허용이 적재나 수정 권한까지 뜻하지도
않습니다.

## 테넌트

| 테넌트 | 담는 지식 | 예시 |
| --- | --- | --- |
| `company` | 회사 업무와 사업 맥락 | 제품, 전략, 경쟁, 법무 |
| `personal` | 개인의 삶과 우선순위 | 자기계발, 개인 기록 |
| `shared` | 여러 영역에 적용되는 일하는 방식 | 방법론, 도구론, 에이전트 하네스 |

주제가 “무엇을 만드는가”보다 “어떻게 일하는가”에 가깝다면 `shared`를 먼저
고려합니다.

## 핵심 원칙

- 원문은 불변 provenance로 보존합니다.
- 기존 개념 이름을 재사용해 그래프 분절을 막습니다.
- 사실, 추론, 추천, 미해결 gap을 서로 섞지 않습니다.
- 가능성을 단정으로, 상관을 인과로 바꾸지 않습니다.
- 외부 검증이 없는 회상과 제3자 평가는 그 한계를 표시합니다.
- lint 통과보다 tenant, path, 근거, 남은 불확실성을 먼저 확인합니다.
- 적재는 준비 단계입니다. 연결을 확인한 뒤 사용자의 원래 질문까지 처리합니다.

## 안전 규칙

- `docs.py load`에는 항상 `--tenant`를 지정합니다.
- 전체 `build.py` 리빌드는 실행하지 않습니다.
- 서로 다른 테넌트 사이에서 문서를 재적재해 이동하지 않습니다.
- 원문이 말하지 않은 claim을 만들지 않습니다.
- 모호한 테넌트나 원본 범위는 적재 전에 확인합니다.

온톨로지 저장소의 `~/.ontology/AGENTS.md`는 권위 있는 구조 지도와 공통 명령
정본입니다. 실제 라우팅 워크플로와 세부 규칙은 그 문서가 가리키는 파일을
따릅니다. 이 README의 예시는 운영 명령을 대체하지 않습니다.

## 사용 예

```text
이 전략 질문에 답하기 전에 온톨로지에서 관련 결정과 근거를 찾아줘.
```

```text
이 보고서를 온톨로지에 적재해줘. 회사 자료야.
```

```text
이 에이전트 운영 방법론을 shared에 추가하고 기존 검증자 개념과 연결해줘.
```
