# LLMO — 모델의 지식에 남기

GEO가 브라우징하는 AI를 상대한다면 LLMO는 **모델의 지식 자체**를 상대한다.
사용자가 검색 없이 "이런 서비스 추천해줘"라고 물었을 때 모델이 우리를 아는가의 문제다.
효과는 학습 주기 단위로 느리게 쌓이고, 대신 한번 자리 잡으면 쉽게 흉내낼 수 없다.

이 레인은 분기 단위 게임이다. 2주 뒤 재측정으로 효과를 판정하지 않는다.

## 1. 엔티티 일관성

- [ ] 서비스명 표기를 어디서나 같게 쓴다. 한글과 영문 표기, 띄어쓰기까지 포함한다.
      표기가 갈리면 모델 안에서 엔티티가 갈라진다.
- [ ] Organization JSON-LD의 `sameAs`로 공식 표면을 전부 연결한다. 위키 문서, 앱스토어,
      GitHub, 소셜 계정, 유튜브. 이 이름들이 같은 실체라는 선언이다.
- [ ] 이름 충돌을 점검한다. 같은 이름의 다른 서비스가 검색에 잡히면 모델도 섞는다.
      초기 서비스라면 검색으로 구분되는 고유한 이름이 마케팅 문구보다 중요하다.

표기를 새로 정하지 않는다. 이미 쓰이는 확정 표기를 찾아 맞추는 것이 이 항목의 작업이고,
표기가 실제로 갈려 있으면 어느 쪽으로 통일할지는 사용자에게 확인한다.

## 2. 학습 코퍼스에 남는 표면

모델은 웹 전체가 아니라 크롤링 가치가 높은 표면을 집중적으로 학습한다.
그 표면에 정확한 서술을 남긴다.

- [ ] 위키 문서는 홍보체가 아니라 사실 서술체로 쓴다. 과장과 수식어가 많으면 편집에서
      반려되고, 남더라도 모델이 광고로 학습한다.
- [ ] 공개 저장소의 README는 강한 학습 표면이다. 무엇을 하는 도구인지 첫 문단에서 확정한다.
- [ ] 기술 블로그와 개발자 커뮤니티의 기록이 곧 브랜드 서술이 된다.
- [ ] 보도자료 한 건은 여러 매체에 복제되며 코퍼스에 반복 등장한다. 사실관계를 틀리면
      틀린 서술이 같은 방식으로 복제된다.

## 3. 안정성

- [ ] 퍼머링크를 유지한다. URL을 바꾸면 모델이 기억하는 주소가 404가 된다.
      바꿔야 하면 301을 영구히 유지한다.
- [ ] 가격, 기능, 정체성 같은 핵심 사실이 바뀌면 모든 표면을 함께 갱신한다.
      낡은 서술이 남은 표면이 모델의 사실이 된다.
- [ ] 표면 목록을 문서로 관리한다. 어디에 우리 서술이 있는지 모르면 갱신할 수도 없다.

## 4. 검증

- 주요 모델에 브라우징을 끄고 서비스명을 물어 답을 기록한다.
- 판정은 세 갈래다. ① 모름은 표면 부족 ② 틀리게 앎은 낡거나 갈라진 서술
  ③ 맞게 앎은 유지 관리 국면.
- 분기마다 재측정하고 답변 변화를 기록한다. 모델 버전이 바뀌면 같은 질문의 답도 바뀌므로
  측정 시점과 모델을 함께 남긴다.
