# Writing Rules — 작성 규칙

경력 기술 작성, bullet 개선, 표현 강화 시 참조한다.

---

## 불확실성 처리

### [확인 필요] 표시 규칙

불확실하지만 사용자 확인 시 강화 가능한 부분은 `[확인 필요]`로 표시한다.

```
[확인 필요: 개인 주도인지 팀 기여인지]
[확인 필요: 성과 수치가 있는지]
[확인 필요: 운영 범위가 어디까지였는지]
[확인 필요: 실제 의사결정 권한이 있었는지]
```

`[확인 필요]`가 있는 문장은 초안으로 취급한다. 제출용 문안에는 해당 주장을 제외하거나,
이미 확인된 범위까지만 낮춰 쓴다. 확인할 수 없는 부분은 초안에서 상태를 유지하되
확정된 사실처럼 매끈하게 숨기지 않는다.

### 애매성 탐지

아래 표현은 필요 시 추가 정의를 시도할 수 있다:

> 개선, 최적화, 운영, 설계, 협업, 구축, 자동화, 고도화, 안정화,
> 리딩, 사용자 경험, 성능 향상, 효율화, 관리

**단, 모든 표현을 해체하려 하지 않는다.**

- 업계에서 일반적으로 통용되는 표현은 과도하게 해체하지 않는다.
- 채용 판단에 실제 영향을 주는 불명확성이 있을 때만 추가 질문한다.

## 성과 유형 분류

| 유형 | 설명 |
|------|------|
| 정량 성과 | 수치로 측정된 개선 |
| 정성 성과 | 사용자/조직/팀의 체감 개선 |
| 산출물 성과 | 기능, 문서, 시스템, 프로세스 완성 |
| 운영 성과 | 안정성, 반복 업무 감소, 장애 대응 개선 |
| 학습 성과 | 신입/주니어/전환자에게 유효한 성장 증거 |

성과가 불명확한 경우, 억지로 결과를 만들지 않는다.
대신 확인 가능한 요소 중심으로 작성한다:
- 수행 범위 / 사용 기술 / 해결한 문제 / 협업 방식 / 산출물

## Writing Heuristics

### 한 Bullet = 하나의 핵심 메시지

한 문장 안에 아래를 모두 과도하게 넣지 않는다:
역할 + 기술 + 성과 + 협업 + 문제 + 도메인 설명

짧고 명확한 문장, 빠르게 스캔 가능한 구조를 우선한다.

### 인간 중심 표현

경험은 단순 작업 목록이 아니라, 조직 안에서의 기여를 드러내야 한다.

필요한 경우 함께 표현:
- 문제의식 / 협업 방식 / 판단 과정
- 트레이드오프 / 사용자 맥락
- 왜 중요한 작업이었는지

모든 경험을 STAR 구조로만 환원하지 않는다.

### 자연스러움 원칙

실제 경험 기반인가 · 검증 가능한가 · 의미 전달이 명확한가가 AI 문체 여부보다 중요하다.

**사용 제한 표현 — 실제 사례 없이 남용 금지:**

> 열정, 혁신, 문제 해결, 사용자 중심, 도전 정신,
> 뛰어난 협업 능력, 다양한 경험, 깊은 이해,
> 적극적으로, 성공적으로, 효율적으로, 최적의, 혁신적인, 빠르게 습득

- "성공적으로"는 구체 결과 없이 사용하지 않는다.
- 제한하는 것: 의미 없는 추상어 · 패턴 반복 · 내용 없는 미사여구 · 과도한 클리셰

### 기술 스택 표현

기술은 단순 나열하지 않는다. 가능하면 포함:
- 실제 사용 맥락 / 사용 기간 / 담당 범위 / 업무 중요도

숙련도는 별점·상중하 대신 실제 사용 프로젝트와 맥락으로 신뢰도를 만든다.

### 삭제/축소 후보

아래 정보는 삭제 또는 축소를 검토한다:
- 직무와 관련 낮은 오래된 경험
- 누구나 쓰는 일반 업무 설명
- 기술명만 나열된 문장
- 결과 없는 반복 표현
- 이미 다른 bullet에서 말한 내용
- 검증 불가능한 성격 표현

### 최근성 원칙

최근 경험일수록 더 구체적으로 작성한다.
오래된 경험은 현재 직무와 관련 있을 때만 강조, 관련성 낮으면 축약.

## 사용자 경험 보호

- 설명이 서툴더라도 실제 경험과 행동 기반으로 강점을 구조화하도록 돕는다.
- 공격적·추궁형 질문을 피한다.
- 경험을 특정 방향으로 유도하지 않는다.
- 사용자의 표현 능력 자체를 역량으로 간주하지 않는다.

현실의 경력 경험은 본질적으로 모호성을 가지며, 완전히 정량화되지 않는다.
채용 의사결정에 필요한 수준까지 명확해지면 남은 모호성은 허용한다.
